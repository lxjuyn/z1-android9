# R7 GNSS and MD1 inventory

The full R7 speaker/PWM package from 21:00 contains the GPS HAL adapter, stock ABI library, mnld, MNL worker, WMT and STP GPS modules, and both stock connectivity patches. Offline extraction found byte-for-byte agreement for both patches against the original Z1 Android 4.4 system. The vendor GNSS service rc contains only a deferral comment and the vendor VINTF manifest has no GNSS entry. Presence of the adapter and HIDL binary alone therefore does not provide framework registration in this profile.

The STP GPS character device and WMT GPS function belong to the connectivity stack. The factory MD1 image in the system firmware directory has a version-2 CHECK_HEADER and requires 8 MiB. The R7 image has no file at that firmware path. Standalone GNSS testing can exercise the existing STP path separately from MD1. An assisted-GPS extension still needs a separately verified ABI adapter and provider. No satellite callback, cellular registration or modem startup has been demonstrated by the inventory.

Run the following from the side worktree against raw ext4 images.

```sh
python3 scripts/diag/z1_r7_gnss_md1_inventory.py /path/to/stock/system.img /path/to/r7/system.img
python3 scripts/diag/z1_stock_ccci_symbols.py /path/to/stock_kernel.bin
```

The checked JSON records each GNSS artifact and both firmware comparisons. The second check reproduced the factory CCIF resource and modem reservation symbols. The stock physical CCIF is at 0x1000c000, interrupt SPI 75, and the modem watchdog uses SPI 120. The runtime reserved-memory base, actual DFO size and power sequence still require verification before an MD1 driver can use them. See [the factory CCCI analysis](Z1_STOCK_CCCI_RESOURCES_20261119.md) and [the GNSS ABI adapter](../scripts/btgps/gps/abi_adapter/README.md).

## Candidate selection and framework gate

The offline builder verifies the selected boot and system hashes and uses the
selected system for the QEMU callback-order test as well as for ext4 staging.
The final factory-HAL loader check uses the output system. Worktree-local
scripts supply the packer, adapter and ABI headers. The separate project
workspace supplies the pinned factory input and compiler.

The first `init.svc.mnld` read can be empty for a disabled service that has
never started. The preparation script requests `start mnld` after verifying
the transport, then requires the real `running` state and socket through the
existing stabilization window. The regression covers both an immediate
request failure and an accepted control request that never creates the
service. An already running legacy `z1_mnld` does not satisfy either check.
The candidate preserves the selected system's GNSS registration policy,
keeps `mnld` disabled for automatic startup, and removes the automatic GPS
prep invocation in older boot inputs.

The prior R7 watchdog log at lines 2298–2304 shows the main thread waiting
inside `GnssGeofenceProvider.runOnHandlerThread()`. Lines 2785–2800 show
`android.bg` waiting for a synchronous Binder reply from
`IGnss@1.0.setCallback`. Android Pie's server implementation first registers
the callback and then calls `mGnssIface->init(&sGnssCb)` before returning.
The board record lacks a matching vendor-side stack, so it cannot separate
a binder/callback wait, the legacy initializer's daemon/socket work, and
driver I/O. Neither the host callback fixture nor the real-library ELF load
calls the real legacy init. [Board capture](../../../mainline_recon/z1_boot_mainline_20261120_000340.log)
[Pie GNSS implementation](https://android.googlesource.com/platform/hardware/interfaces/+/android-9.0.0_r61/gnss/1.0/default/Gnss.cpp#393)

Keep system_server's GNSS registration deferred. A later isolated test needs
timed entry/exit markers around client callback registration and legacy
init, plus a vendor worker stack on timeout, before exposing GNSS to
system_server. MD1 is an independent project. The stock resource and firmware
inventory alone cannot determine a safe modem reservation or bring-up
sequence.
