# v30：HAL 模块符号名 `HMI` 修复 —— v29 的两个关键修复本来会静默失效

日期：2026-11-08  作者：主会话（含 qemu 实机级验证）

## 一句话

v29 里我用手写的最小 AOSP 头（`/tmp/gpsstub/hardware/hardware.h`）编出来的
`gralloc.z1.so` 和 `gps.default.so`，导出符号叫 `HAL_MODULE_INFO_SYM`；
而 Android 的 HAL 加载器 `hw_get_module*()` 是 **`dlsym(handle, "HMI")`**。
⇒ 两个 HAL 都会 "load: couldn't find symbol HMI" 加载失败。

## 证据链

1. **加载器要的字符串确实是 `HMI`**（设备自己的库，不是猜的）：
   ```
   $ grep -aoE ".{8}HMI.{8}" /mnt/v29/lib/libhardware.so
   unknown HMI load: c            ← 旁边就是 "load: couldn't find symbol %s"
   ```
2. **v29 部署的两个 .so 没有这个符号**：
   ```
   $ arm-linux-gnueabihf-nm -D /mnt/v29/lib/hw/gralloc.z1.so | grep -iE 'hmi|HAL_MODULE'
   00005d48 D HAL_MODULE_INFO_SYM        ← 名字错了
   （对照：v25 那个 25,116 B 的 gralloc.z1.so 导出的是 `HMI`，所以历史上能加载）
   ```
3. **qemu + 设备自己的 linker/bionic 跑 dlsym 实测**（`/tmp/btroot`，绕开 bionic pid 限制）：
   ```
   === v29 as flashed ===
   HMI=(nil) HAL_MODULE_INFO_SYM=0x40b7ce00
   RESULT: FAIL (loader would report 'couldn't find symbol HMI')
   === rebuilt with the macro ===
   HMI=0x40b7ce00 tag=0x48574d54 id=gralloc name=Graphics Memory Allocator Module
   RESULT: PASS
   ```
   GPS 桩同样：`HMI=(nil)` → FAIL；重编后 `id=gps name=Z1 GPS stub` → PASS。

## 后果（如果就这么开机）

- `hw_get_module("gralloc")` 变体 `z1` 失败 → 继续找 `gralloc.default.so`
  → 命中 `/vendor/lib/hw/gralloc.default.so`（25,024 B，**ashmem 老版，无 `z1_lima_*`、无 16 像素对齐**）
  → lima 拿到的不是 dma-buf ⇒ 桌面/SystemUI 的 `eglCreateImageKHR` 仍然失败。**gralloc 修复白做。**
- GPS 桩不加载 ⇒ `IGnss` 服务不注册 ⇒ `IGnss::getService("default", false)` 继续阻塞
  system_server ⇒ 每轮 6 次 `WATCHDOG KILLING`。**GPS 修复白做。**
- 这两个都是**静默失败**：只有一行 ALOGW/ALOGE，然后走回退路径，表面现象和没修一样。

## 修法

在 `/tmp/gpsstub/hardware/hardware.h` 补上 AOSP 原本就有的宏：

```c
#define HAL_MODULE_INFO_SYM         HMI
#define HAL_MODULE_INFO_SYM_AS_STR  "HMI"
```

然后**重编**两个 .so（objcopy `--redefine-sym` 不行：它不改 `.dynsym`，
而且 GNU hash 表里的哈希是对老名字算的，光改字符串 dlsym 也找不到）：

```
NDK=/home/lxj/claude/6572/android-ndk-r26d
CXX=$NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/armv7a-linux-androideabi28-clang++
L=/tmp/sysuicrash/grallocbuild/libs          # 设备自己的 libc++/libcutils/liblog

# GPS 桩
$CC -shared -fPIC -O2 -I/tmp/gpsstub -I/tmp/gpsstub/hardware \
    -o gps.default.so /tmp/gpsstub/gps_stub.c -Wl,-soname,gps.default.so

# gralloc
$CXX -shared -fPIC -O2 -DLOG_TAG='"gralloc"' -DZ1_USE_LIMA=1 \
    -I/tmp/gpsstub -I/tmp/gpsstub/hardware -I/tmp/gpsstub/cutils \
    -I/tmp/gpsstub/system -I/tmp/gpsstub/log -I z1a9_gpt/graphics/gralloc \
    -nostdlib++ -o gralloc.z1.so \
    z1a9_gpt/graphics/gralloc/{gralloc,framebuffer,mapper,lima_allocator}.cpp \
    -L$L -lcutils -llog -lm -ldl -lc++ -Wl,-soname,gralloc.z1.so -Wl,--no-undefined
```

产物核对：

| 项 | 旧（v29 部署，坏的） | 新（v30） |
|---|---|---|
| gralloc 大小 | 18,456 | 18,700 |
| gralloc sha256 | `848d11d0…` | `23ba7328…` |
| gralloc 导出 | `HAL_MODULE_INFO_SYM` ❌ | `HMI` ✅ |
| `bic r1,r9,#15`（16 像素对齐） | 有 ✅ | 有 ✅ |
| NEEDED / SONAME | libc,libcutils,liblog,libc++,libm,libdl / gralloc.z1.so | **完全相同** ✅ |
| gps 大小 / sha256 | 4,764 / `e6cb9654…` | 4,756 / `56954258…` |
| gps 导出 | `HAL_MODULE_INFO_SYM` ❌ | `HMI` ✅ |

## 产物与刷写

- `out/z1_v30_hmifix/system_v30.img`，sha256 `9829ccd12857bad4977366e07f6a9744d100288caecdcc209581f00964cfcbb9`，
  e2fsck 干净（2719 文件 / 206493 块）。
- 与 v29 逐块比对：**只有 48MB 块 0 / 2 / 11 不同**，其余 16 块已由 v29 的整分区读回校验证明一致。
  ⇒ 只补写这 3 块并逐块读回 `cmp`，即可断言整分区 == v30。

## 教训（值得记住）

**手写 ABI 桩头文件时，除了结构体布局，还要核对"加载器实际用哪个字符串/符号名"。**
这个项目的 HAL 是 `dlsym("HMI")`；同理 `hw_get_module` 还会校验 `hmi->id == class_id`
（"gralloc"/"gps"），以及 `tag == HARDWARE_MODULE_TAG (0x48574d54)`。
两者都在 qemu 测试里一并断言了。
