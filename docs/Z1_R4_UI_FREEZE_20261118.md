# Z1 R4 UI freeze, November 18, 2026 (UTC+8)

The kernel remained live through the reported freezes. UART shell returned uptime
864.43 seconds. Android's SurfaceFlinger repeatedly died with SIGSEGV, and init
then restarted zygote and several dependent services. The GPU restart watcher
reached its trip threshold but R4 intentionally only logs the trip, leaving Mesa
selected. This is a separate observed failure from the earlier `shutdown,battery`.

Local evidence (workspace `mainline_recon/`):

- `z1_boot_mainline_20261118_225911.log:2983`: boot complete at 200.96 s;
  capture was interrupted on the host after logging through 335 s.
- `z1_boot_mainline_20261118_230902.log:187`: SurfaceFlinger SIGSEGV at 543.94 s;
  repeated at 551.96, 553.99 and 559.31 s. At lines 593–595 the watch trip is
  logged without a fallback. The device did not reboot between these events.
- Lines 1467–1482: repeated null dereference at address `0x8`, frame `#00`
  in `/system/vendor/lib/libgallium_dri.so`; logged PC `0xd28288`, mapping
  offset `0x850000`. The ELF executable segment has a `0x1000` virtual/file
  offset difference, so ELF PC is `0xd29288`; register LR normalizes to
  `0xd97834` using the same load bias. Exact symbols are PC
  `nir_block_cf_tree_next+0x5c` and LR `process_loops+0x14d0`; the preceding
  `BL` at `0xd97830` is the `nir_block_cf_tree_next` call from the
  `nir_foreach_block_in_cf_node` loop in `gather_unroll_heuristic_info`
  (`nir_loop_analyze.c:1412`). The faulting instruction is
  `ldr ip, [r2, #8]`: `r2` was loaded from `[r0, #12]`, i.e.
  `block->cf_node.parent`, and was NULL. This identifies an invalid parentless
  control-flow node at the consuming loop-analysis pass; it does not establish
  which earlier pass or input created it. Do not feed the logged `0xd28288`
  directly to `addr2line`: without the executable segment's `+0x1000`
  adjustment it incorrectly resolves to unrelated `nir_instr_free_and_dce`.
- Lines 4042–4043, 4979 and 5507: repeated board Gallium SHA256
  `bba2904c6de95e600afe43db1bf3dd169ee5f7cc33e4cc89939110a033b9fff7`;
  EGL SHA256 `bb0ac77c03e79648db5dc8a480ec478be566b78c6105e9f781fd22100b46f445`.
  Gallium extracted from R4 `system.img` hashes to
  `492f0b5e871868f55023351722a609da6b65e186fbf31366a28d7faf981232b9`.
  Both builds share ELF build ID `e7cb1faad408fbfa59030add3ba5d1231f1f32a9` and
  the board's six words at the faulting file offset match the extracted file
  (lines 6240–6242, 6260–6261). This supports the symbolization while leaving
  the whole-file discrepancy unresolved. At sampling `/system` was mounted RO.
- Lines 2354–2374: during this later run, battery was present, charging,
  `4242000 µV`, reported capacity `100`, USB online. This is not a sample from
  the earlier shutdown. Offline R4 extraction identifies the earlier health HAL
  (`667c104b…`); the source-side capacity fix still needs build and board validation.

The file mismatch was narrowed to exactly one 4096-byte page at file offset
`0xb07000`: substituting only the captured board page into the extracted library
reproduces the full board SHA256 `bba2904c…`. Its bytes match the system image at
`0x2e79501c` (unrelated firmware text, not aligned to a filesystem block). The
expected Mesa page maps to ext4 block `205000`, offset `0x320c8000`; a buffered
read from `/dev/block/mmcblk0p4` at this offset returned the correct hash while a
normal file read returned the wrong one (lines 17057–17059). The target's `dd`
did not support `iflag=direct`; no direct-read result was obtained.

At uptime 2060 s, writing `1` to `/proc/sys/vm/drop_caches` caused the next
file read to return the canonical R4 library hash `492f0b5e…` (lines 28688,
28743). The restart counter stopped at 301 and SurfaceFlinger PID 32121
responded to dumpsys using `Mesa, Mali400, OpenGL ES 2.0 Mesa 26.1.1`
(lines 28759–28764). This is an in-session recovery with no flash or system
file changes. It rules out a persistent difference in that on-disk library
page as the explanation for the earlier file hash. It does not explain how the
wrong contents entered the file read path. Check persistence through active UI
use, then investigate the Linux read/DMA and memory paths before changing the
Mesa compiler. Keep the battery shutdown as a separate validation item.
