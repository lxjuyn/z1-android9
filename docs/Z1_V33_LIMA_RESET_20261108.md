# v33：lima PP 卡死不可恢复的根治 + GPU 门禁不再把设备拖进重启循环

日期：2026-11-08

## 上板现象（证据）

开机约 190 秒后（= 应用开始渲染的时候）：
```
[190.806] lima 13010000.gpu: ppmmu0 page fault at 0x2098940 from bus id 0 of type read
[190.807] lima 13010000.gpu: pp0 task error 0 int_state=0 status=1
[190.810] lima 13010000.gpu: pp0 bus stop timeout
```
之后**每一个** PP 作业都 10.24 秒超时，共 37 次，屏幕永久冻结在最后一帧；
SurfaceFlinger 丢帧（`Fence: Throttling EGL Production: fence ... didn't signal in 3000 ms`），
SystemUI 的 RenderThread `Abort message: 'Failed to wait for the fence 0x3000'` → 崩 → 连带重启。

**关键交叉验证**：第一条 fault 前面**没有** `job timeout` 行（因为 `pipe->error` 已为 true，
`lima_sched.c` 的 `if (!pipe->error)` 把日志吞了），而后面每一次都有 —— 说明
"第一次是 fault 触发、之后全是同一个死状态被反复超时"这个模型是对的。
`status` 也从 1 变成 5（BIT2 驱动未定义，是 fault 之后才锁存的）→ PP 再也没跑起来过。

## 根因（三重死锁，逐条对上代码）

1. `lima_pp_hard_reset()` 写 `PP_CTRL_STOP_BUS` 后只等 **100 微秒**；超时就直接 `return ret`，
   `PP_CTRL_FORCE_RESET` **永远执行不到**（`lima_pp.c`）。
2. `lima_sched_timedout_job()` 里顺序反了：先 `pipe->task_error()`（PP 硬复位），
   后 `lima_mmu_page_fault_resume()`（MMU 硬复位）。而 page fault 的事务正卡在 MMU 里
   （驱动从不发 `LIMA_MMU_COMMAND_PAGE_FAULT_DONE`），PP 的 STOP_BUS 因此永远不 ack。
3. 唯一的兜底（TOPRGU MFG 复位）挂在 runtime/system suspend 上，而卡死的 job 一直占着
   `credit_count`，`lima_device_suspend()` 直接 `-EBUSY` 返回 ⇒ 复位一次都发不出去。

## 修法（3 个文件，全部在本轮内核里）

| 改动 | 文件 | 作用 |
|---|---|---|
| MMU 复位挪到 `task_error` **之前** | `lima_sched.c` | 解开 page-fault stall，让 STOP_BUS 能 ack |
| bus stop 超时后**仍然写** `PP_CTRL_FORCE_RESET`，并返回 `-EBUSY` | `lima_pp.c` | 不再"半途放弃" |
| 新增 `lima_device_reset()`：TOPRGU MFG assert/deassert + 逐 IP 重新初始化；PP 硬复位失败时升级调用 | `lima_device.c/.h`、`lima_pp.c` | 最坏情况也能把 GPU 拉回来 |

> 注意：`dev->reset` 是 `devm_reset_control_array_get_optional_shared()` 拿的，
> 必须 assert+deassert，不能用 `reset_control_reset()`（会在 `deassert_count != 0` 时 WARN 并失败）。

## 同批修掉的 system 侧问题（都会独立导致"开不了机"）

1. **`z1_gpu_gate.sh` 永不隐藏 mesa**：它藏掉 mesa 后装的 SwiftShader 三件套在本镜像里
   `dlopen` 不进去（`F libEGL: couldn't find an OpenGL ES implementation`），SF 直接崩 →
   无限重启。实测已复现。现在只写 `/cache/z1_gpu_gate.status` 取证，绝不改 EGL 目录。
2. **`z1_gpu_watch.sh` 改 log-only**：trip 时不再写 disable 标记、不再 autoreboot。
3. **服务加 `oneshot`**：以前脚本一退出 init 就重启，日志里几十条 `starting service 'z1_gpu_watch'`。
4. **镜像构建自动补 SELinux 标签**：`debugfs write` 不带 `security.selinux`，换过的文件会变成
   `unlabeled`（实测 apps 加载 `/system/lib/hw/gralloc.z1.so` 报 `tcontext=u:object_r:unlabeled:s0`）。
   `tools/z1_make_system_image.sh` 现在按路径自动打标签并 `ea_list` 回读校验。

system 相对板上 v30 只差 5 个 48MB 块（0/2/11/15/16），其中包含一个**对照实验**：
`/lib/hw/gralloc.z1.so` 从 16 像素对齐改回 2 像素对齐（`bic r1,r9,#15` → `#1`），
其余指令逐条比对一致。目的：判断 `ppmmu0 page fault` 是不是 16 对齐那版 gralloc 引入的。

## 上板判据

1. 若 **不再出现** `ppmmu0 page fault` → 根因是 gralloc 的 16 像素对齐，转去按 PP 真实要求修；
2. 若仍出现 fault，但之后 **不再有**成串 `pp0 job timeout`、屏幕继续刷新 → 本轮的恢复链生效；
3. dmesg 里应出现 `ppmmu0 resume` 在 `pp0 task error` 之前；最坏情况出现 `full GPU reset via TOPRGU MFG`。
4. 无论如何 **不应** 再出现"藏 mesa"（`gate: ACTIVE: libGLES_mesa.so hidden`）。
