# Z1 Android 9 stability comparison

The November 15 adaptation R3 pair is the best directly identified Android 9 rollback comparator found in the captures reviewed here. The device reached the desktop and remained up into the second hour. It also eventually reset. This pair can test the change in failure frequency without switching to Android 4.4 or erasing userdata.

The November 15 original pair is in `out/adaptation_candidate_20261115_r3/` (`boot_pkg/boot.img` and `system.img`). The matching archive is `bridge_backups/products/products_adaptation_r3_20261115_181052/candidate/`. The file hashes match the recorded flash result, and `e2fsck -fn` on the system image returned zero. The board also received a touch-navigation rc change during that session. A reflash of the original pair would restore the image as shipped, before the live edit. The original system is paired with the original boot. Mixing either half with R7 introduces ART and staging differences.

The R3 and R4 zImages are byte-identical (`0e93afcedbc877ec67cec6b216366ed4d309d22dc851c3c39e2cd21cc6680ed8`). Their appended trees differ only in the initrd end address. The R4 freeze therefore occurred with the older kernel and board configuration still present. The R4 report identifies a corrupt cached page as the immediate cause of the SurfaceFlinger loop. It does not identify the origin of that page corruption. November 21 R7 R2 also read a mismatched `framework-res.apk` from its file cache while the corresponding sampled raw window matched, even with HSQ disabled. The same capture later recorded an ext4 journal abort and emergency read-only `/data`. These failures can explain a visually stuck system with a running kernel and differ from a return to Preloader.

The November 15 log `mainline_recon/z1_boot_mainline_20261115_215411.log` identifies the flashed boot at lines 8–10. At lines 1712–1715, a falling charger-detect edge followed by recovery leaves Linux running. At lines 1719–1721 a second falling edge is followed by Preloader. An older November 8 boot also returned to Preloader after a charger-detect drop at 2535.95 s (`z1_boot_mainline_20261108_150838.log:24872–24904`). The same sequence recurs in R7 at 252.60 s. This places the charging transition symptom before the recent Bluetooth, speaker and lock-screen changes. It leaves battery, input supply, PMIC behavior and any software contribution unresolved. The other recent resets have no recorded falling edge. The raw Preloader RGU status was zero in the recent trace, so ordinary watchdog expiration with a retained reset latch has less support.

The R7 `#169` zImage (`b6b5174e8f394a70e8bde22bf2ff472a60aeb500d31ed1088090a0abb654c63e`) differs from the `#166` comparator. Both use a 1-bit eMMC bus. The R3 tree caps it at 50 MHz and the board reports HSQ enabled. R7 caps it at 25 MHz, reports HSQ disabled and adds the speaker GPIO and wider AFE range. R7 also carries a different boot ramdisk and system image. The apparent stability difference cannot be attributed to any one of these changes from the archived runs alone.

For the next board session, keep the current R7 pair available and capture the first R7 cold boot on battery with the target USB cable disconnected. For a software regression comparison, use the verified November 15 pair under the same power conditions and repeat with steady external power. Preserve userdata before changing the boot/system pair, and record ART and filesystem responses on both starts. A short desktop observation is insufficient given the 1655 s R7 reset and the 6828 s older reset. After any failure, check whether the serial log returns to Preloader, the framework PIDs change, or the compositor stops while the kernel and clock continue. Apply individual feature changes to the first baseline that remains usable and repeat the same workload after each.

The checked R3 package is archived on the project HDD at `z1-archive/android9-r3-stability-comparison-20261123_151658/`. The scatter enables only bootimg (offset `0x2980000`, capacity 6 MiB) and android (offset `0x4340000`, capacity 900 MiB). The saved copies and scatter pass `sha256sum -c SHA256SUMS`. If SP Flash Tool is used, select **Download Only** with this scatter. The preserved `/data` may contain ART files from later Android 9 builds, so record any framework startup errors separately from a return to Preloader.
