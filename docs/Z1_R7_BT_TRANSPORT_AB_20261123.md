# Z1 R7 Bluetooth transport comparison

The radio-enabled UART trace from November 21 (`z1_boot_mainline_20261121_222143.log`, lines 1087–1101) records the factory initializer's own Reset command, factory initialization success, Android's subsequent HCI startup and then a timeout for Android's Reset. A separate exclusive direct H4 attempt returned a Reset completion. Both paths need comparison through Android on the same board build.

Commit `450e4e8` adds the volatile property `debug.z1.bt.transport`. With the value `direct`, the next vendor `USERIAL_OPEN` selects direct H4 even when factory NVRAM is ready. With the property unset, the adapter tries factory initialization when NVRAM is ready. This allows a comparison without changing calibration files or readiness. The diagnostic log identifies the direct selection and reports whether NVRAM was ready.

The archive on the project HDD is `z1-archive/products_btvendor_independent_20261123_154437_NPvRMvZv/`. Its `package/boot.img` hashes to `98aa0d0aed409feacee34d75fa26cd1ecd0b90378e41e8a048f6349b8f97c046`. Its base and rollback boot is the radio-enabled ART cache boot `472075ae9c3e74012ab0147469390b817d3b88b8781bbbf5b3c1c6f1b0254791`. Both pair with system `f48322725f2f5f53d2d4b3c3b9d92379e0aea715b9d3b04ada03755381843cab`. The boot only replaces the Bluetooth vendor ramdisk payload and adjusts the initrd end address. The retained boot stage installs it in `/system/vendor/lib/libbt-vendor.so`. Verify the active library SHA-256 `3b5eb59f7dca1776f0a969136dabd4fea743b8aa849447a9e3b27e04a164b9cb` before comparing modes.

ARM API 28 ELF verification and ten host cases passed, including factory-first and direct selection with ready NVRAM. Two vendor builds and two independent boot packaging runs gave byte-identical respective binaries. Package readback passed.

After a stable radio-enabled boot, keep Wi-Fi off and confirm `sys.z1.radio.bt_nvram_ready` is `1`. Enable the Bluetooth package for user 0 if it was left disabled in the radio-off diagnostic session. On equivalent cold starts, compare the default mode with `setprop debug.z1.bt.transport direct` issued before Bluetooth is enabled. Record WMT power-on, adapter choice, Android HCI Reset and the first subsequent command in both runs. If both time out after WMT is ready, stop Android Bluetooth, verify it released `/dev/stpbt` and use the existing standalone write and writev probes. Keep direct H4 as a diagnostic until the board's address, discovery, pairing, reconnect and audio are verified.

## R7 integrated image: privileged enable with screen locked

The board used boot `4a669340…` and system `d6f08965…`. UART capture `z1_boot_mainline_20261123_184337.log` records the event on boot ID `b565430b-a1a2-4399-8c4a-448bfc698c6d`.

- The root command ran as UID 0 and `svc bluetooth enable` returned 0. The HAL opened `/dev/stpbt`. At 1141.62 s the WMT function-on timed out; the initial open failed before Android could send HCI Reset (lines 2622–2671).
- The subsequent connectivity-chip reset was internal to CONNSYS: Linux kept the same boot ID. Wi-Fi recovered, and two later BT opens reported WMT success and STP ready (lines 2673–2755). On the later Android attempt `event_finish_startup` preceded `BLE_START_TIMEOUT`; Bluetooth returned to `OFF` (lines 2769–2796 and 2854–2866). The HAL startup callback alone does not prove a response to HCI Reset or controller readiness.
- `settings get global wifi_on` reported `0`, but `/z1_wifi_probe.sh` had already issued `1` to `/dev/wmtWifi`, completed scans, and left the connectivity driver's Wi-Fi function enabled. The driver itself logged Wi-Fi recovery. `wlan0` later having IFF_UP clear also does not prove a WMT function-off. Do not count this as the Wi-Fi-off leg.

For the next cold-boot leg suppress only the automatic `/z1_wifi_probe.sh` invocation, leaving the launcher, firmware, WMT modules and factory Bluetooth path intact. Verify no Wi-Fi function-on trace before Bluetooth enable; avoid using a post-recovery retry as the cold control. Keep the measured WMT response, HAL callback, first HCI command/response and framework timeout as separate markers. Test default versus direct H4 only after identifying which run reaches WMT-ready. Restore and verify Wi-Fi coexistence before calling this a fix.
