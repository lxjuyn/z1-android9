# Z1 R7 recovery and board acceptance

The starting point is the installed radio-off ART boot (`0840aee4…`) and factory-repair/Settings system (`f4832272…`). The UART log `z1_boot_mainline_20261122_165453.log:25–106` shows a return to Preloader during an unlock/Home attempt with Bluetooth disabled. On the host the CH340 subsequently stopped enumerating. No new image was flashed during this review. Keep the same-system radio-on ART boot (`472075ae…`) available for the separate radio run.

1. **Freeze and reset.** Reconnect the UART, record boot ID, boot and system identity, framework PIDs, pstore, voltage and storage readback. Repeat `dismiss-keyguard` and Home separately with a marker before and after each command. Use battery-only boot and compare with the powered setup without changing the image. A return to Preloader is a failure even when boot completes afterward. `RGU STA=0` and a missing panic record do not identify the reset cause. Prior Linux output shows the ramoops console registered, so inspect which records survive the return to Preloader before changing reserved memory. Compare cached and raw file data if hashes diverge. Investigate a confirmed rail drop or repeatable bad read before changing regulator, watchdog, eMMC queue or timing behavior.
2. **Lock and wake.** Confirm the exact composer and boot contents. The currently paired factory boot already contains the `display_blank` ownership line, so do not add the same fix again. Run the lock probe for repeated cycles and require Android Asleep/Awake to agree with the physical gate on a single boot. Confirm the panel actually goes dark and the first new frame appears after wake. Then repeat with the physical power key to cover its input policy.
3. **Page lag.** Record input, launcher/Settings foreground status, per-frame timestamps, SurfaceFlinger present fences and I/O stats during identical scroll sequences, while carrying boot/PID identity across each interval. Separate missing frames or process resets from late frames; discard lock-screen and zero-frame samples. HWC source has synchronous acquire waits and CPU staging copies; timestamp both before selecting a graphics optimization. Compare p50/p95 and stalls against the same workload and display refresh period before accepting a change.
4. **Speaker and Android media.** On the existing system, transfer the current diagnostic without touching partitions. Test direct PCM and Android playback separately with headphones out, then sample actual mapped HAL, PCM hardware pointer, DAPM, GPIO140 and PMIC. Place a microphone next to Z1 and compare the recording against a known tone and silence segment. If digital state passes but the tone is absent, inspect the analog path and power rather than treating tinyplay exit status as audible output.
5. **Bluetooth and Settings.** With a stable baseline, use the matching radio-on boot and verify the actual adapter, kernel modules and NVRAM readiness. With Android Bluetooth stopped and no other `/dev/stpbt` opener, use separate equivalent cold boots for `z1_bt_hci_probe --exclusive-controller` and the same probe with `--writev` to separate the two send paths. Re-enable the package only on radio-on, collect the first Android enable attempt from WMT through HCI and feature negotiation, then test the exact Settings path, scan, pair and reconnect with a known peer. An HCI reply alone is not a Bluetooth pass.
6. **Integrated retest.** Only after the independent tests pass, repeat cold boots, page interactions, lock, speaker, Bluetooth and Wi-Fi coexistence together; run a sustained uptime check. Record pass/fail separately with image and runtime hashes. Keep GPS out of this repair cycle.

Upstream references checked for this procedure: Linux [ramoops](https://docs.kernel.org/admin-guide/ramoops.html), AOSP [graphics synchronization and present fences](https://source.android.com/docs/core/graphics/sync), and the Android 9 HIDL `VendorInterface`/H4 flow (repository reference copy under `bridge_backups/bt_audit_20261110_205049/ref`).

## November 23 UART reset follow-up

The same radio-off boot and system reproduced whole-device resets. The UART reader stayed attached to the CH340 across the transitions. No partitions were flashed. Local evidence is `mainline_recon/z1_boot_mainline_20261122_235804.log`.

- Lines 213–266 record `wm dismiss-keyguard` returning zero, the old boot ID and both framework PIDs, and the eventual return to Preloader. No Home or swipe command was sent. The next boot ID differs and Android reaches `sys.boot_completed=1` again around 218 s (lines 2087–2093 and 2225).
- Lines 3495–3528 show a reset immediately after the installed audio diagnostic started tinyplay and its register reader. The host recording has no sustained 500 Hz tone. In a separate attempt without the register reader, the root daemon started the test script and the board reset before the log established that tinyplay had started (lines 5551–5591). Neither attempt establishes a speaker or playback verdict, or that the register reader caused the reset.
- On a later boot, Android completed at 218 s and the board returned to Preloader again without a new unlock or playback command. The last kernel messages were `charging DISABLED (read back)` and `charger unplugged (RGS_CHRDET CHR_CON0[5] -> 0)` at 252.60 s (lines 7489, 7601–7602 and 7633). Preloader then started again before Linux (line 7726). Record whether the power cable was physically moved and compare a locked idle boot with independent battery power. Keep the UART adapter attached. The charger transition may be a marker of the supply change rather than the initiating fault.
- Preloader reports `RGU STA: 0` and `WDT does not trigger reboot` on these transitions. The inspected pstore after the first reset contained only `pmsg-ramoops-0` (lines 3373–3378). The source of the reset remains unproven. Use passive capture for the power comparison before resuming active audio and UI tests.

## Offline power and reset audit

The archived boot `0840aee45d58f56230cc294fb4c97d0365349eae90cff4c6382600b819629260` matches the first 5,986,304 bytes of the saved partition readback. The extracted kernel contains the charger detection, disable readback, and disable failure messages. The appended DTB reserves 1 MiB for ramoops and specifies a 256 KiB console, a 128 KiB pmsg area, and 128 KiB dump records. The UART confirms console registration. The pstore listing after the first observed reset contained only pmsg. Ramoops requires preserved RAM and a successful dump, so this listing leaves the reset cause open.

In `fork_linux/drivers/power/supply/z1_charger.c`, `z1_charger_update()` first reads the PMIC's read-only `RGS_CHRDET` bit and passes that sample to `z1_charger_apply()`. When the sample is offline, apply disables active charging, then update prints the offline transition. This explains the message order at lines 7601–7602. The offline sample came first. The log cannot distinguish a cable movement from input dropout or an unexpected PMIC state. The first Preloader start then reports `Unknown boot!` and `pl_power_off` at lines 7694–7695. The next Preloader start reports `USB/charger boot!` at line 7848 and proceeds to Linux. Count the intervening start as a Preloader power-off and restart sequence. The other three Android resets in this capture have a charger-classified next boot without a logged falling CHRDET edge.

The original `1/preloader_j72_z1.bin` (SHA-256 `c917f1d2efd3d573d10c28777c24aab33de21b2b925e9367f757a616db578e92`) reads RGU status at `0x1000700c` and prints the raw value at Thumb file offsets `0xcbd4–0xcbde`. This occurs before the watchdog mode write at `0xcc76` in the same routine. The watchdog classification at `0xcd0e–0xcd12` depends on the status masked with `0xc0000003` at `0xcb68–0xcb72`. An RGU status of zero is evidence against an ordinary SoC watchdog expiration with a retained latch. Earlier boot stages and a loss of latch state remain outside this observation.

Run the same read-back image first on battery alone with the serial adapter connected and the target USB cable absent. Compare it with a separate idle run on stable external power and record physical cable changes independently of CHRDET. The earlier capture `z1_boot_mainline_20261122_154148.log` contains resets near 225, 245 and 1655 seconds, so a two-minute idle run cannot clear the failure. If it recurs, capture battery and input voltage through the transition if measurement equipment is available. A matched stock boot and system under the same power conditions can distinguish a fault shared with stock from behavior specific to the port.
