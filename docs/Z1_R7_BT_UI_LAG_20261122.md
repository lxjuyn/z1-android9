# R7 board follow-up: Bluetooth abort and UI lag

This follow-up used the previously read-back radio-off boot (`0840aee4…`) and unchanged system and userdata. No partition was written. The Bluetooth package remains disabled for user 0 as a persistent diagnostic setting; after restoring a radio-enabled boot, run `pm enable --user 0 com.android.bluetooth` before any Bluetooth acceptance test.

## Bluetooth

The radio-off boot's previous-boot pmsg preserves the full causal chain: the HIDL service loads the Z1 adapter; it falls back to direct H4 and `open(/dev/stpbt)` returns `ENOENT`; the vendor returns zero transport descriptors; HIDL initialization fails; then `com.android.bluetooth` aborts in `hci_layer_android.cc:78`. BluetoothManager retries. This result is expected for a radio-off kernel with Bluetooth still advertised to Android. Disabling the package stopped the observed crash loop. This does not identify the first failing operation on the radio-enabled boot. On that build, kernel `BT_open` first timed out at WMT, then reported WMT success and STP ready on the retry. The kernel result alone cannot establish that the vendor library returned a descriptor or that the HCI callback succeeded.

With the package disabled, launching `android.settings.BLUETOOTH_SETTINGS` resolved to `Settings$ConnectedDeviceDashboardActivity`. Events show creation at device time 18:10:52.830 and the app's `onCreate` at 18:10:59.784; the activity was paused behind the locked screen and logged `am_failed_to_pause`. The diagnostic `am start -W` did not return before it was interrupted. The Settings process remained alive and ran `onResume` and `onStop`; the sampled events did not show a Settings crash. `SystemServiceRegistry` also reported no USB service; its relationship to the reported failure is unproven. The connected-device dashboard on this build is not a substitute for reproducing the user's exact tap path with Bluetooth enabled.

Cross-check of the older radio-enabled logs identifies a confirmed Settings failure: `ConnectedDeviceDashboardActivity` crashed in `UsbBackend.updatePorts()` because the USB service was unavailable and `UsbManager.getPorts()` was invoked on null (`..._20261121_225400.log:4853–4875`). The null guard is in `c19a9544`. The installed APK hashes to `6e9aa0dba297e8eb840b565b625716a7939e32a91bdc531187437721663e4b7a`, matching the combined repair image on disk, while `service check usb` still reports `not found` (`..._165151.log:13–17`). Together with the lifecycle events above this is partial board evidence for that guard. Full verification still requires an unlocked, visible Settings page and the exact tap path with Bluetooth enabled.

A separate radio-enabled run reached `event_finish_startup` through the factory adapter, but the subsequent Android HCI Reset (`0x0c03`) timed out (`..._20261121_222143.log:1091–1101`). An exclusive direct-H4 probe in another run returned Reset and Read Local Version, and got status `0x30` for extended feature pages 2 and 3 (`..._20261121_225400.log:14663–14670`). That combination narrows the remaining work to transport and stack behavior on the actual radio-enabled build, including differences between the factory setup, direct probe and Android. It does not show that the controller cannot answer Reset or that feature pages caused every attempt to fail.

## UI lag and resets

- The dashboard's nearly seven-second create delay was observed after disabling the Bluetooth package. The Bluetooth crash loop does not explain all UI stalls. Separately, the radio-off boot returned to Preloader with wireless modules absent; the reset source is still unknown.
- The launcher was hidden (`visibility=8`), with keyguard's StatusBar focused. `gfxinfo` reported zero frames, so its percentiles and jank counters cannot be used to estimate desktop FPS. A synthetic swipe did not produce a valid launcher sample.
- There are two independent storage observations: boot-time top showed I/O wait at 62 out of 200 aggregate CPU points, and an earlier run returned a wrong cached `framework-res.apk` hash that matched the offline image after clean page cache was discarded. Prior builds also returned wrong pages for other system files. These are reasons to compare raw and cached reads and log block latency during a stall. They do not establish that eMMC hardware, HSQ, or the GPU is the cause.
- This follow-up found only `pmsg-ramoops-0`, with no kernel panic record in pstore. Presence of a pmsg file and the reported `reboot,edl` boot-reason string do not identify the reset source. Previous pmsg also includes an EGL fallback message; Lima probe and simultaneous EGL fallback logs do not identify the renderer used by the launcher.

Keep the next tests independent. For radio-enabled Bluetooth, record the actual mounted HAL and vendor binaries' hashes, run an enable attempt with logs spanning WMT, vendor descriptor return and HCI initialization, then follow the exact Settings tap and capture its process events. For performance, collect real launcher frames on an unlocked, foreground launcher while correlating input, SurfaceFlinger presentation, renderer, I/O wait and block latency. Record PID and uptime across the same gesture. A fresh boot or isolated frame counter is insufficient to qualify this release.

Local UART evidence: `mainline_recon/z1_boot_mainline_20261122_154148.log` (I/O and Bluetooth loop), `..._013552.log:2846–2953` (radio-enabled open and retry), `..._164212.log:16–45,201–286` (hidden launcher and keyguard), and `..._164734.log:51–76,108–135` (Settings events and pmsg HCI failure). Local logs are not bundled with this report.

## Unattended UI test

The subsequent UART session (`..._165453.log:16–106`) verified that the board was up at 1,877 s, the Bluetooth package was disabled, keyguard held focus and the ALSA card and `tinyplay` were present. The diagnostic sequence `wm dismiss-keyguard; input keyevent KEYCODE_HOME` was sent at about 1,901 s. RenderThread and Binder messages followed. The sequence never returned its final marker or a new window focus; the same UART stream instead returned to Preloader, which reported `RGU STA: 0` and `WDT does not trigger reboot`. Linux then started again. This is an unattended reproduction of the UI stability failure with Bluetooth disabled. The sequence does not identify which action or concurrent process caused the reset. No playback command or frame test completed before reset. This is a failed UI stability gate, and no FPS or speaker pass can be reported for this run.
