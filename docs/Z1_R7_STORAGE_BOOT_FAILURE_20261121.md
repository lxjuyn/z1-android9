# Z1 R7 Priority R2: two storage failures during the same boot

The flashed R2 pair is identified by boot SHA256 `2d99381361466a05861af7fe17a51e5924e4e6094a47287edfdf1759e60294c3` and system SHA256 `56bde54564f31bd68c5d1af2693e32628a27ed36f470799e6030d602ed0fda21`. SP Flash Tool reported success for `bootimg` and `android`; that is not a full readback. Do not promote R2 as a stable release.

The matching raw read covers one window and used the block device cache. It does not prove all flash contents are correct. The cause of bad file data, whether the `/data` inconsistency is on disk, and whether the two storage symptoms share a cause remain open. On the preceding boot `/data` passed the recorded repair with rc=0; another fsck alone cannot qualify this build.

Next board session: keep the package and `/data` intact; collect a backed-up, unmounted `/data` image before running a read-only fsck on the copy. Compare repeated aligned O_DIRECT raw reads with buffered raw and file reads, and retain any mismatched page bytes. Repeat the workload with one eMMC variable changed at a time (start with a conservative clock at unchanged bus width and HSQ state). Record reset evidence separately. A candidate must complete repeated cold boots and at least one sustained interactive run with stable framework PIDs, matching known file hashes, and no ext4 emergency read-only event before checking Bluetooth, speaker, and lock-screen behavior. Cache eviction is a diagnostic intervention, not a fix.
