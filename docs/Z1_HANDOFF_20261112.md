## 4. 本轮（2026-11-12）完成的工作

### 4.1 CPU 动态调频：1001MHz 固定 → schedutil 806–1300MHz

**根因链（很重要，别再踩）**：

1. CPU 的时钟源头**就是 `armpll`**：`cpu_mux`（`infracfg 0x0` bits[2:3]）父 = `clk26m / armpll / univpll / mpll_d2`。
2. **`cpufreq-dt` 在此 SoC 上会死机**：它直接 `clk_set_rate(cpu_mux, …)` → 透传到 armpll 的 PLL 寄存器 → PLL 重锁期间 CPU 停止取指。实测：
   ```
   rcu: INFO: rcu_sched detected stalls on CPUs/tasks:
   rcu: 0-...0: (0 ticks this GP)
   Sending NMI from CPU 1 to CPUs 0:
   ```
3. 正解 = **`mediatek-cpufreq`**：它先把 CPU 时钟 reparent 到 `intermediate`
   （`CLK_TOP_MPLL_D2`），改完 PLL 再切回 armpll。驱动里**早就有 MT6572 表**：
   ```c
   { .compatible = "mediatek,mt6572", .data = &mt6572_platform_data },
   ```
   **唯一缺的是 `CONFIG_ARM_MEDIATEK_CPUFREQ` 没开**（`CONFIG_CPUFREQ_DT` 要**关**）。
4. 驱动用 `regulator_get_optional(cpu_dev, "proc")` ⇒ DTS 必须是 **`proc-supply`**。
   （`cpu-supply` 是 `cpufreq-dt` 的 `find_supply_name()` 认的名字，写错就 `-ENODEV` 不 probe。）
   本板 DTS 早在 11-08 就有 `proc-supply = <&mt6323_vproc_reg>`，无需再加。
5. **OPP 电压必须 ≤ `mt6572_platform_data.proc_max_volt = 1250000`（1.25V）**。
   写 1.30/1.35V 会让 ondemand 一上来就 panic：
   ```
   regulator_check_voltage from regulator_set_voltage_unlocked
   regulator_set_voltage from mtk_cpufreq_set_target
   Code: ... (e7f001f2)        ← BUG()
   Kernel panic - not syncing: Fatal exception
   ```
   最终 OPP：`598/806/1001/1209/1300 MHz`，**全部 `opp-microvolt = <1150000>`**（低风险配置，与 11-08 结论一致）。
6. `opp-supported-hw` + `nvmem-cells = <&cpu_speedbin>` **必须删掉**：本板 socinfo/efuse cell 解析不了，
   OPP core 会把**所有**档位丢弃：
   ```
   cpu cpu0: _of_add_opp_table_v2: no supported OPPs
   cpu cpu0: OPP table can't be empty
   ```
   （见 `arch/arm/boot/dts/mediatek/mt6572.dtsi` 的 `cpu_opp_table` 注释。）

### 4.2 调频策略：schedutil + 806MHz 地板（同一套 A/B 实测）

用 `dumpsys gfxinfo com.android.launcher3` + **15 次自动 `input swipe`**（不依赖人手）对比：

| governor | 总帧 | 卡顿帧 | 90th | Slow UI thread |
|---|---|---|---|---|
| `ondemand`（598M 地板） | 354 | **79 (22.3%)** | 19ms | 0 |
| `schedutil`（806M 地板） | 349 | **57 (16.3%)** | 19ms | 3 |

`schedutil` 跑在调度器路径里（不是轮询），配合抬高地板后接地更快，**仍然动态**（空闲降到 806MHz）。
已写进开机脚本。省电取向可改回：`echo 598000 > .../scaling_min_freq`。

### 4.3 GPU devfreq（26 / 416 MHz）

`gpu_opp_table` = `26MHz` + `416MHz`，gpu 节点加 `operating-points-v2`。
`lima_devfreq` 就会注册（`_opp_set_regulators` 的 `-ENODEV` 是**允许**的，代码里明确 continue）。
开机脚本把它固定到 `performance`（=416MHz）。

**为什么不用 simple_ondemand**：26MHz 对 Mali-400 太低，每次触摸/动画头几十毫秒都在 26MHz，
主观更卡。要省电再手动切：`echo simple_ondemand > /sys/class/devfreq/13010000.gpu/governor`。

### 4.4 GPU 超频 491.52MHz —— 已验证失败，别再试

时钟树里 `mfg_sel` 二选一（`upll_d3`=416MHz / `mfg_mux_sel`），而 `mfg_mux_sel` 的 8 个父时钟里有
`mfg_pre_491m`=491.52MHz 等更高档。加 OPP 并让 performance 顶上去后实测：

```
Total frames rendered: 5     Janky frames: 5 (100.00%)
50th percentile: 300ms       Number Missed Vsync: 4
```

每帧 300ms = **GPU 命令超时**。⇒ 这块 Mali-400 MP1 的稳定上限就是 **416MHz**（额定值）。
该 OPP 已从 DTS 删除；**不要重新加**。

### 4.7 内存：实测**不是**瓶颈，但配置有问题（已改）

```

zram 262144 kB, Used = 0
```

## 5. 必须遵守的操作纪律

### 5.1 boot.img 打包（踩死过两次）

MTK 的 boot 镜像里 **kernel 段前面必须有 512 字节 MTK 头**：

```
88 16 88 58 | <载荷长度 LE u32> | "KERNEL" | ...    ← 512 字节
```

Android 头的 `kernel_size` = **载荷 + 512**，`ramdisk_size` = ROOTFS blob（含它自己的 512B 头）。
少这 512B 时 LK 直接报 `KERNEL partition magic error` 并**无限重启**（板子看着像变砖）。

现成脚本（别再手打）：`/tmp/z1_pack_ok.py`（内容见 §7），或项目里的 `tools/z1_pack_mtk_bootimg.py`。
**打完必须反解确认**：`kernel 段前 14 字节 = 88 16 88 58 …KERNEL`，且 `dtb magic d00dfeed`
出现在 `kernel_size - dtb_size` 处。

坑：`/tmp/z1_pack_ok.py` 第一版把 ramdisk 路径**硬编码**了，改完脚本打包却用了旧 ramdisk
（镜像 sha 和上一版一模一样）。**打包后必须反解 cpio 确认新内容在里面**。

### 5.2 刷写

```sh
tools/z1_flash_chunked.sh <partition> <img> [chunk_mb] [maxtries]
# bootimg:  OFF=0x2980000 SIZE=0x600000   （4MB×2 块）
# android:  OFF=0x4340000 SIZE=0x38400000 （48MB 分块）
```
- **两个刷写任务不能并发**！实测并发会交叉写同一分区（状态文件里出现"块=4/2"），结果不可预期。
  刷前 `pgrep -af z1_flash_chunked` 确认没有残留在跑。
- 刷写需要板子进 preloader（`lsusb` 看到 `0e8d:2000`）；开机循环时 preloader 每 10s 出现一次，
  脚本的重试能抓到；正常开机状态下要**手动复位**。
- **刷写过程会长时间占住串口**，串口日志会丢，别误判。

### 5.3 正常开机

**必须拔掉板子的 USB 线**（插着会走 LK 的 charger-boot：`[PLFM] USB/charger boot!` → 不进系统）。
刷完刷写工具会复位，之后拔线、按电源键。

优先用 `reboot` 而不是拔电——硬断电会脏 `/data`（ext4 journal 重放，开机脚本会检测并 `e2fsck`）。

### 5.4 串口 / 板载 root 通道

```sh
# 抓日志（会重新设波特率，适合重枚举后）
z1a9_gpt/scripts/z1deploy/z1cap.sh ~/claude/6572/mainline_recon/z1_boot_r14_verify.log
# 以 shell(uid 2000) 身份执行一行命令
z1a9_gpt/scripts/z1deploy/z1sh.sh 'ls /sys/class/devfreq/'
# 以 root 身份执行：写 /data/local/tmp/z1stage/cmd.sh，守护进程(z1_rootd)取走执行，结果在 out.txt
z1a9_gpt/scripts/z1deploy/z1sh.sh 'printf "%s\n" "cmd1" "cmd2" > /data/local/tmp/z1stage/cmd.sh; echo Q'
sleep 14; z1a9_gpt/scripts/z1deploy/z1sh.sh 'cat /data/local/tmp/z1stage/out.txt'
```
- 写 `/sys/...`（cpufreq/devfreq）**必须走 root 通道**，shell 用户是 `Permission denied`。
- 串口在长命令/大量输出时会**丢字符甚至楔住**（shell 回显但不执行）——表现是命令被打断成乱码。
  所以：命令写短、用 `printf "%s\n"` 一次写多行到文件再执行、必要时 Ctrl-C 或 reboot 恢复。
- root 通道有 120s 上限；长任务用 `nohup setsid sh -c '...' &` 丢后台写文件，之后再 `cat`。

### 5.5 DTS 编辑

用 Python 正则删 DTS 块**极易漏掉收尾 `};`**，本轮踩了两次（一次导致整个文件损坏，从 git 还原；
一次导致 dtb 编译失败）。规矩：
1. 改前 `cp` 到 `bridge_backups/`；
2. 删块用**完整块匹配**而不是从注释到第一个 `};`；
3. 改完立刻 `make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- mediatek/mt6572-z1.dtb`；
4. **用 `dtc -I dtb -O dts` 反解确认**目标属性真的在/不在。

```python
page = struct.unpack('<I', base[36:40])[0]
mtk_hdr = bytearray(base[2048:2048+512])          # 复用已验证的 512B MTK kernel 头
zimg = open('fork_linux/arch/arm/boot/zImage','rb').read()
dtb  = open('fork_linux/arch/arm/boot/dts/mediatek/mt6572-z1.dtb','rb').read()
payload = zimg + dtb
struct.pack_into('<I', mtk_hdr, 4, len(payload))
kern = bytes(mtk_hdr) + payload
rd = open(rd_path,'rb').read()
hdr = bytearray(base[:2048])
struct.pack_into('<I', hdr, 8, len(kern))
struct.pack_into('<I', hdr, 16, len(rd))
img = bytearray(hdr) + kern + b'\x00'*(math.ceil(len(kern)/page)*page-len(kern)) \
    + rd + b'\x00'*(math.ceil(len(rd)/page)*page-len(rd))
open(out_path,'wb').write(bytes(img))
print(f"{out_path}: {len(img)} B  kernel={len(kern)} ramdisk={len(rd)} <- {rd_path}")
```
