## 0. 先明确"3D 加速"在这台机器上的含义

| 项 | 事实 | 证据等级 |
|---|---|---|
| GPU | ARM Mali-400（Utgard 架构，MT6572 集成） | 已验证：`GL_RENDERER=Mali400`（`mainline_recon/z1_lima_offscreen_240x320_render_20260717_231744.log:16`） |
| API 上限 | **只有 OpenGL ES 2.0 / ES 1.1**。Mesa 官方 Lima 驱动文档：Utgard 不支持 GLES3、Vulkan、OpenCL | 官方：docs.mesa3d.org/drivers/lima.html |
| 与 2D 的关系 | OVL（OverlayEngine）负责**合成/扫描输出**，Mali 负责**渲染**。二者不是一回事，不可互相替代 | 架构事实 |
| 框架要求 | A9 HWUI 与 SurfaceFlinger 都只要 ES2 即可工作；HWUI 默认 `skiagl`，可切 `opengl` | 官方 r61 `EglManager.cpp:41`、`RenderEngine.cpp:47` |

**结论：3D"完整"= GLES2 全功能可用（不含 ES3/Vulkan），并且能与现有 OVL 合成链路正确同步。**
强行宣称 ES3/Vulkan 属于虚报能力，会让应用选择不存在的路径而崩溃——禁止。

## 1. 当前基线：2D 做到了什么，3D 卡在哪

### 1.1 已达成（可复核）

- 4 层全部走 OVL 硬件平面：`frames=10997 commit_fail=0 device=4 client=0`
  （`mainline_recon/z1_boot_v83.log:54728`、`:55919`）。
- KMS 四平面 + 物理连续 dma-buf：`plane 35/41/47/53`，`dma_addr=0x9a300000/0x9a200000/
  0x9a400000/0x9a150000`（`z1_boot_v83.log:54911-54948`）。
- 导航栏 240×48 低于内核 64×64 下限，用补齐到 240×64 的空转 buffer 解决
  （`releases/ovl_v83_r14/README.md:60-66`）。

### 1.2 必须纠正的既有说法（审计结论）

| 旧说法 | 实测/审计结论 | 依据 |
|---|---|---|
| "11009 帧全程 4 层 DEVICE" | `device=4` 只是**快照**；日志同段有 `frame 6000: device=1` 和 `DEVICE -> CLIENT (not importable as contiguous dma-buf)` | `z1_boot_v83.log:53532`、`:12127`、`:25112` |
| "全程零拷贝" | 小层走 `small_layer_sync()` 做 CPU 拷贝；`device=4` 不等于零拷贝 | `releases/ovl_v83_r14/README.md:60-63` |
| "release/present fence 已完成" | r14 二进制 `present/retire` 返回 -1；r16 的 vsync 线程从未出现 `first vsync ts=` | `releases/ovl_v83_r14/README.md:70-73`；`docs/ovl/Z1_SESSION_20261110_OVL_RESULT.md:67` |
| "Mesa 26 必须升级才能用" | 24.0.9/26.1.1 都缺"能证明本机 0x4000 根因已修"的证据；升级≠修复 | Mesa issue #2701（Mali450 同样 4000/3） |

### 1.3 3D 的六个真正卡点（按依赖顺序）

1. **Kernel/lima 内存契约**：lima 用 shmem/SG 按页映射 GPU VA
   （`lima_gem.c:118`、`lima_vm.c:127`），而 OVL 要求整块物理连续
   （`mediatek/mtk_gem.c:218`）。MTK IOMMU 当前关闭（`.config:5602` 关、DTS `:424` disabled）。
   ⇒ **不是任意 lima BO 都能被 OVL 扫描**。
2. **gralloc 构建分叉**：`graphics/gralloc/Android.mk:26-35` 只加 `lima_allocator.cpp`，
   漏了 `z1_heap.cpp`；`gralloc.cpp:171` 走弱符号 `z1_heap_alloc_ex`，缺实现时**静默回退 ashmem**。
3. **GP 非法命令流**：`lima_regs.h:86` 定义 `0x4000 = LIMA_GP_IRQ_PLB_INVALID_CMD`；
   `gp.c:34-43` 视为不可恢复。r16 内核已有 reset 补丁（MMU 先恢复 `sched:465`、
   PP stop 超时强制 `pp:191-225`、TOPRGU 全复位 `device:484`），但 `gp.c:189-193`
   GP stop 超时仍直接返回、`:228` 忽略 task_error 返回值。
4. **人为同步缺口**：HWC `wait_fence()` 把任何 `poll>0` 当成功
   （`scripts/z1hwc2/z1hwc2.cpp:1257-1276`），超时后仍关 fd 继续读写 buffer
   （`:2472-2486`）；小层 250ms watchdog 超时放行（`:536`）。
5. **buffer 导入失败仍提交**：`client_target_fb` 双路径都失败时
   `present` 清空 client FB 后继续（`z1hwc2.cpp:2490-2497`）。
6. **部署/回滚语义**：`.disable_hwcomposer` 只删一个 `/vendor` 覆盖文件
   （`scripts/z1deploy/z1stage_boot.sh:154-166`），不切 Mesa、不恢复 gralloc；
   `z1_install_hal.sh:112` 不建 disable 标记，重启会重新安装。

## 2. 目标架构（分层，逐层可独立验收）

```
应用 (GLES2)
   │
   ├── HWUI（debug.hwui.renderer=opengl）──┐
   │                                       │
   └── SurfaceFlinger RenderEngine ────────┤  ← Tier 3：框架层
                                           ▼
                       libGLES_mesa.so（当前 Android EGL/GLES 入口）
                                           │            ← Tier 2：用户态驱动
                       libgallium_dri.so + libdrm（静态）
                                           ▼
                       动态发现的 lima render 节点（不固定编号）  ← Tier 1：内核渲染节点
                                           │
                        dma-buf（PRIME）────┤
                                           ▼
                        gralloc.z1.so 分配（CMA/连续）  ← Tier 0：buffer 契约
                                           │
                        HWC2（z1hwc2）→ DRM atomic → OVL 平面  ← 现有 2D 链路
```

**关键原则：3D 渲染产物必须经"能扫描"的 buffer 交给 OVL；不能假设任意 BO 可扫描。**

## 3. 分阶段实施（每阶段都有通过门禁与回滚）

> 纪律：一个阶段只改一件事；每阶段结束**必须**留下：源码 commit、产物 sha256、
> 板上日志文件名、判定结果。门禁不过就不进下一阶段。

**做什么**

   例如 `out/Z1_STATUS_OVL_20261110.md` 记的 v83 哈希 `b8d04db5…` ≠ 实际 `ad3eed1a…`）。
2. 冻结三份基线：r14 boot（`6c85b6a0…` / 5,900,288 B）、v79 boot（`d332b5e9…` / 5,808,128 B）、
   现行 system_v35。
3. 把 `docs/gpu/` 与本文件一起提交，作为后续所有阶段的引用基准。

**门禁**：分别保存本地产物 SHA、板上读取文件 SHA、`uname -a`、build id、反解 boot 与实际进程 maps。属性/内核版本字符串不能代替逐文件身份。冻结配对的 boot、system、Mesa、gralloc/HWC、持久 active/install.sh/禁用标记与属性；r14/v79 只作历史候选，先验证完整组合。
**回滚**：无需（只读）。

### P1 —— 内核 lima 与 buffer 契约（1～2 天，低风险，不动显示链）

**做什么**
1. 确认 `CONFIG_DRM_LIMA=y/m`，按 DRM driver/sysfs 与 render/KMS 能力发现节点，不固定 `card0/renderD128`；
   `dmesg | grep -i lima` 有 probe（历史 s6_v8 判据同上）。
2. 决定渲染 buffer 来源，二选一（**推荐 A**）：
   - **A. 显示侧分配 → lima 导入**：CMA/dumb（`dma_alloc_wc`）分配 → `PRIME_HANDLE_TO_FD`
     → lima 作为 render target 导入 → 渲染 → OVL 扫描。与现有 2D 路径一致，风险最低。
   - **B. lima 分配 → 显示导入**：需要 IOMMU 或连续内存保证；当前 IOMMU 关闭，
     必须先证明 lima BO 物理连续，否则 OVL 会 `-EINVAL`。
3. 首测固定 LINEAR、offset=0；非零 offset 支持另设边界/溢出/尺寸回归后修改 `mtk_plane.c`。
4. 独立审计 GP/PP reset 的跨 pipe 协调、错误返回、MMU 恢复；没有最小复现前不以强制 reset 掩盖非法命令。
5. 在任何 OVL 共享异步渲染 buffer 之前，必须完成 P6A 的 acquire/失败帧/旧 buffer 生命周期门禁；单纯同步离屏可先进行。

**门禁**（全部通过才进 P2）
- `dmesg` 无 `gp error irq state=4000`；
- 一个 240×320 RGBA8888 的 dumb/CMA buffer 能被 lima 写入，CPU 读回像素正确；
- 同一 buffer 能被 DRM `AddFB2` 接受并被 OVL 扫描（用 `z1kmstest` 或现有 KMS 调试口）。

**回滚**：使用 P0 实测验证的完整组合；只换 boot 时必须证明对应 system、持久覆盖及内核模块 ABI 未改变。

   且历史日志出现过 `Mesa/Mali400/26.1.1`
   （`mainline_recon/z1_boot_mainline_20261108_105346.log:5879`）。
   缺的不是版本，而是**像素正确性、精度与同步的验证**。

2. 用实际 `meson-private/cmd_line.txt` 重建，**`gles1=enabled`**（旧 README 写 disabled 是错的）；

### P6A —— 同步正确性（P3/P4/P5 的前置门禁，可与同步离屏并行）

**做什么**（每一项单独提交）
1. `wait_fence()` 检查 `POLLERR/POLLHUP`，超时**不得**继续读写该 buffer
   （`z1hwc2.cpp:1257-1276`、`:2472-2486`）。
2. `client_target_fb` 失败时中止本帧并记录，而不是清空后继续（`:2490-2497`）。
3. present fence 必须绑定**实际 atomic commit**，不能由定时 vsync 线程凭空 signal
   （`:578`）。
4. release fence 语义：保护"上一帧"buffer（Android 官方 `hwcomposer2.h:1437-1449`）。
5. 若启用 DRM `OUT_FENCE_PTR`，先确认驱动真的在 flip done 时 signal。

**门禁**
- 延迟 fence、POLLERR/POLLNVAL、导入失败、静置超过250ms、关闭 vsync、失败 commit、重复 buffer 等用例均证明未完成写入不被读取、仍扫描的 buffer 不被提前复用；
- 连续 30 分钟播放动画 + 快速滑动，无撕裂、无白帧、无 `commit_fail`；
- `dumpsys SurfaceFlinger --latency` 有稳定 vsync；
- 人为注入慢 GPU（大纹理）时仍不出现"读别人正在写的 buffer"。

**回滚**：恢复已验证的完整同步路径；关闭 fence 不能作为异步生产者的安全回滚。

**P6B（可后置）**：在 P6A 正确性已过后优化 vsync 频率、唤醒与延迟。实际 OUT fence/翻页事件必须证明旧 buffer 已不再被扫描；本次显示开始不代表新 buffer 已可重写。

## 4. 已知风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| GP `0x4000` 复现 | 画面花屏/黑屏 | P1 的 reset 补丁 + P2 的逐项压测；逐项使用已核实的 `LIMA_DEBUG` 诊断开关作单变量定位，不能一次全开后称根因已解 |
| 供电/传输原因尚未闭环 | 刷写失败、测试中断 | ADC、Discharging 与 USBError 单独不能证明真实供电或唯一根因；独立测量并记录连接状态。boot≤6MiB，写请求后失败按未知/可能部分写处理并完整读回 |
| 6MiB boot 分区 | 加内核功能可能超限 | 沿用 slim config + XZ；新增功能优先放 system/vendor |
| HWC fence 缺陷 | 撕裂/白帧/错误复用 | P6A 未过不得启用异步共享buffer；P6B节奏优化可后置 |
| 文档哈希与字节不符 | 误判版本 | 每阶段以 `sha256sum` + 反解为准，不引用旧文档哈希 |
| 回滚不完整 | boot与system/持久覆盖不兼容 | P0冻结并验证完整组合；原厂boot配修改system不能称恢复原厂 |

| P3 | gralloc 构建修复、handle 校验、导入测试（3 个） | Sonnet |
| P4/P5 | 测试 APK、属性与能力声明 | Haiku + Sonnet |
| P6 | fence 修复、vsync 绑定、回滚开关（3 个，同文件**串行**） | Sonnet + Opus 复核 |
| P7 | 压力矩阵、性能对比 | Sonnet |
| 全程 | 独立复核（交叉验证） | Opus |

**同文件只允许一个 agent 改**；`z1hwc2.cpp` 的所有 fence 改动必须串行。

---

## 6. 明确不做（避免虚报与返工）

- 不实现 GLES3 / Vulkan / OpenCL（硬件不支持）。
- 不把 "OVL 4 层硬件合成" 当作 3D 加速的证据。
- 不做视频硬解（MT6572 编解码走 OMX，与 Lima 无关）。
- 不在没有 fence 闭环前宣称"稳定 60fps"。

---

## 7. 验收总表（最终交付必须全部满足）

1. GLES2 应用能画、能交互、前后台切换不崩；
2. `GL_RENDERER` 明确为 Mali400，`ro.opengles.version=131072`；
3. 连续 30 分钟无 GP/MMU 错误、无 commit 失败；
4. 有 fence 的完整链路（acquire → GPU → OVL → release），并有日志/时间戳佐证；
5. 每份产物有 sha256 + 板上读回校验；
6. 验证完整回滚集合（boot/system/库/模块/持久覆盖/属性）并在重启后核对实际加载身份；禁止仅按 boot 名称宣称可恢复。
