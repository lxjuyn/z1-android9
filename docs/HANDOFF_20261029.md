## 2. 本会话已完成的修复（已入库 + 已 push）

### 2.1 三个"沉默失败"级 bug（最严重）

**B1 — ramdisk 里 5 个启动脚本被内核静默丢弃（R4 起就存在）**
- `z1_ramdisk_edit.py` 写 cpio newc 的 mode 字段时只写权限位 `0o755`，**缺 `S_IFREG`**。
- 内核 `init/initramfs.c` 的 `do_name()` 只识别 `S_IFREG/S_IFDIR/S_IFBLK/CHR/FIFO/SOCK`，
  裸 `0o755` 不匹配任何分支 → **文件解包后根本不存在，且内核不报错**。
- 受影响 5 个：`z1_wpa_start.sh` / `z1_wifi_pre.sh` / `z1_wifi_connect.sh` /
  `z1_gps_prep.sh` / `z1_audio_probe.sh` → **WiFi 用户态 + GPS + 音频取证三条链一起断**。
- 修：工具加 `_fix_mode()`，对**所有**输出记录（含继承记录）规范化补 `S_IFREG`。
  同时修了把它判成 PASS 的 `verify_r4f_indep.py`（原断言 `fields[1]==0o755` 为通过条件）。
- git：`012ce81`（z1a9_gpt）

**B2 — 内核从仓库不可复现（重编 = 起不来）**
- 三个断点：① `SND_SOC_MT6323_ACCDET` 的 Kconfig 符号**只存在于临时补丁**，从未入库；
  ② `codecs/Makefile` 未注册该对象；③ AFE 的 F3 修正（`of_address_to_resource(dev->of_node,…)`）
  没回灌主树 → 从仓库重编得到**无音频**内核。
- 更严重：`z1_defconfig` 是一份**陈旧的早期全量 dump**（1379 行），`make z1_defconfig` 生成结果里
  `MMC_BLOCK=n`（挂不上 rootfs）、`WATCHDOG=n`（正是 CLAUDE.md 记录的 WDT 回归 bug）、
  `KERNEL_XZ=n`（zImage 进不了 6MB 分区）、`LOCALVERSION=""`（vermagic 失配，全部 .ko 作废）。
  与交付内核配置差异 **1697 项**。
- 修：Kconfig/Makefile/F3 入树；用交付内核配置 `make savedefconfig` 重建为 500 行标准 defconfig。
  **round-trip 验证：生成结果与交付内核配置只剩 1 项差异**（`CHARGER_Z1_MT6323=m`，本会话有意新增）。
- git：`291233f8a`（音频入树）、`c1596c1f2`（defconfig 重建）

**B3 — PMIC 诊断会自伤开机路径**
- 我一度把 `mt6397_irq_init()` 改成写失败即 `return ret` → 会让整个 MFD probe 失败，
  连带打死**电源键 / PMIC 键盘 / RTC / 给触摸供电的 regulator**。
- 修：改回**非致命**（`dev_err(…, "(continuing)")`，不 return），保留诊断价值（失败打印 errno）。
- git：`f2800e694`

### 2.2 WiFi 是一次回归（本会话最重要发现之一）

**R5 交付件里的 `mtk_stp_wmt_soc.ko` 用的是上游 A 版 EMI 基址 `0x80080000`**，
该地址落在内核管理的 RAM 里（非 no-map）→ `arch/arm/mm/ioremap.c:318` 的
`WARN_ON(memblock_is_map_memory(...) && mtype != MT_MEMORY_RW)` 触发 → `ioremap` 返回 NULL
→ 驱动打印 `EMI mapping fail` → **WiFi 完全不可用**（固件从未下载，`wlan0` 不出现）。

**而 2026-08-14 已在 Z1 上跑通过**的版本用的是 **B 版 `0xbe080000`**
（落在已交付 dtb 的 `connsys@be000000` no-map carveout 内，物理正确）。
完整成功日志 `mainline_recon/z1_boot_mainline_20260814_202853.log`：
`Open FW image done, 160464 bytes` → `WMT turn on WIFI success!` → `wlan0` → `iw scan` 扫到 **12 个真实 AP**。

**主会话实证**：R5 镜像内那枚与 `out/z1_wifi_stage/modules/mtk_stp_wmt_soc.ko`
**sha256 完全相同**（`786e9ab4…`）——即 R5 跑的正是报错那枚。
回归之所以可能：**外编 .ko 不入 git**（修复 commit `e3198bbc3` 只提交了 dts）。

**已修**：`out/z1_r5_system/system.img.r5f_final`（换入 B 版 `c9c62c26…`，**不需要动 dts/dtb**）。
重放脚本 `z1a9_gpt/scripts/r5f_wifi_emi/apply_wifi_emi_fix.sh`。

⚠️ **上板判据陷阱**：成功时**不会**打印 `EMI mapping OK`（该串在全部 5 枚 .ko 里都不存在，
debug 级被编译掉，8-14 成功日志里 0 次出现）。**判据是"没有 `EMI mapping fail` 行"。**

## 3. ★ 未完成 / 待接手的事项（按优先级）

### P0-A：音频真出声（**最高价值，且已只剩最后一步**）

**现状**：内核侧已齐备（ASoC/MT6323 codec、11 个 snd*.ko、`/lib/libtinyalsa.so`、
`/bin/tinyplay` 全在位）；**唯一缺口是一个能用的 primary HAL**。

**为什么原来的 HAL 不行**（已论证，别再走）：
- `/vendor/lib/libaudio.primary.default.so`（20,844 B）是 **AOSP null 空壳**
  （导出 `HMI`，`open/ioctl/read/write/mmap` 导入**全 0**）。板载实锤
  `AudioFlinger: loadHwModule() error -22 loading module primary`（r_submix 却成功加载）。
- LOS14 的 763,948 B **真 HAL 不可用**：① 它走 `/dev/eac` 私有接口，而我们 mainline 内核
  **0 处 `/dev/eac`**；② A7/A9 `audio_hw_device` ABI 差一个指针（152 vs 156 B）。
  还有 220 个 UND 符号里差 10 个 A7-only 的 `AudioSystem::*VoiceUnlock*`/`IATV`。

**已就绪的替代方案**：自写 tinyalsa 薄 HAL，**PoC 已交叉编译通过**：
- 源码 `z1a9_gpt/scripts/r5d_audio_hal/audio_primary_z1_poc.c`（316 行）
- 产物 `z1a9_gpt/scripts/r5d_audio_hal/libaudio.primary.z1.so`（**11,812 B**）
- 部署脚本 `z1a9_gpt/scripts/r5d_audio_hal/apply_audio_hal.sh`
- **主会话独立复核过**：导出 `HMI`；UND 只有 `pcm_open/pcm_write/pcm_close/pcm_is_ready/pcm_get_error`
  + libc/log/pthread；NEEDED = `libtinyalsa.so/liblog.so/libm.so/libdl.so/libc.so`；
  `/dev/eac` 字符串 **0 处**。**是干净的。**

**接手要做**：
1. **判定 PoC 的 `HMI` 头 `id` 字段**：PoC 写 `"z1-mt6572-mainline"`，在役 stub 是 `"audio"`。
   查 `libhardware` 的 `hw_get_module_by_class` 逻辑 —— AudioFlinger 是靠 `id` 匹配还是靠
   文件名 `audio.primary.<name>.so`？**若靠 id，PoC 必须改成 `"audio"`**。
2. 校验 `audio_hw_device` 结构字段顺序与 **A9 头**一致（156 B）。本机找头：

### P0-B：UI 卡顿 / GPU 加速（**用户感知最痛，且已查明是回归**）

**量化证据**（板载 log `OpenGLRenderer: Davey! duration=`，10-25）：
```
样本 32；最小 1,303ms；中位 5,112ms；最大 31,534ms；平均 7,872ms
>1s 的帧 32/32 (100%)；>5s 的帧 17/32     （正常应 <16ms）
```
伴随 `ActivityManager: ANR in com.android.systemui` ×3 +
`Watchdog: *** WATCHDOG KILLING SYSTEM PROCESS`。**这是"机器能开但一直卡/重启"的根因。**

#### ★ 关键结论：这是 GPU 加速**回归**，板子曾经跑的是硬件渲染

**铁证**（主会话已独立复核两条 log）：
```
10-20 (正常):  SurfaceFlinger: vendor = lima / renderer = Mali400
               version = "OpenGL ES 2.0 Mesa 19.1.8"
10-25 (卡顿):  SurfaceFlinger: vendor = Google Inc. / renderer = Google SwiftShader
               version = "OpenGL ES 2.0 SwiftShader 4.0.0.4"
```
即：**10-20 时 lima/Mali-400 硬件渲染是跑通的**，当前 `system.img.r5d_final` 换成了一套**不兼容的栈**。

#### 两条**已排除**的错误方向（别浪费时间）

- **`/dev/dri/renderD128` 不是问题**：有专门 ueventd 规则、SELinux 已给它 `gpu_device` 标签、
  且 7 月实测 `renderD128_open_rw=PASS`。主会话先前看到的"板载 log 0 命中"是
  **grep 假象**（无人打印该路径 ≠ 节点不存在）。精确 mknod 值：**renderD128 = 226,128**、`card0` = 226,0。
- **GPU 时钟 25.39 MHz 与本次卡顿无关**：`a9_wt`/`fork_linux` 两树的 gpu 节点与时钟驱动
  `diff -rq` **零差异**、都没有 `assigned-clock-rates`，而**同样的源码 7 月出 416 MHz**
  → 是运行期差异，不是静态配置缺失。关键佐证：**10-20 那次 mesa 生效时同样是 25.39 MHz**，
  25 MHz 下照样出 Mali400。**不建议现在动 clocks**（还会牵动 initrd-end）。
