⇒ **首启 = 已知可用的 goldfish HWC1**（能开机、能亮屏），新 HAL 必须用 §5.2 在线激活一次。这不是 bug，是设计的 fail-safe；但如果你以为"刷完就会跑新 HAL"，会误判 §3 的 (c)(d)。

> `strings -a out/z1_v83test/stage/hwcomposer.z1.so | grep -E "first commit done|debug.z1.hwc"`。

### 2.2 刷写方法 A（本板最近 10 次刷写实际用的那条路：按字节偏移写 0x2980000）

### 2.3 刷写方法 B（备用：按分区名 `bootimg`，自带回滚）

本板有 GPT 名 `BOOTIMG`（scatter 第 173-183 行：`linear_start_addr: 0x2980000`、`partition_size: 0x600000`），`flash_with_retry.sh` 的注释也把 `bootimg` 列为合法分区名；`tools/z1_flash_chunked.sh` 的分区表里同样写着 `bootimg) OFF=0x2980000; SIZE=0x600000`。

它比方法 A 多做三件事：**预擦除**（`mtk.py e bootimg`）、**完整分区读回比较**（超时按镜像大小算：`60 + size/1MB` 秒）、**失败自动回滚**（写回第 3 个参数）。

### 2.4 读回验证铁律

| 要求 | 说明 |
|---|---|
| **必须逐字节一致** | 方法 A 靠 `cmp -s`，方法 B 靠 `cmp -s -n`；只要不一致就 **不得开机**，按 §2.5 重来 |

### 2.5 preloader 僵死恢复规则

| 现象 | 含义 | 动作 |
|---|---|---|
| `mtk.py` 一直在 `Preloader - Status: Waiting for PreLoader VCOM…` + 点号 | **正常等待**，还没抓到窗口 | 不要干预；插 USB / 按电源键 / 重新上电 |
| 连上后（出现 `DaHandler`/进度条）**45–60 s 一个字节都没前进** | preloader 僵死 | **长按电源 10 s 断电** → 等 3 s → 重新插 USB/上电；脚本会在下一轮重试 |
| `DeviceClass - USBError(...)` / 中途掉线 | USB 链路抖（本板常态） | 拔插一次；脚本下一轮自动重来 |
| 300 轮（~25 min）都没抓到 | 板子没进 download 模式 / 线不对 | 确认是 download 线（不是充电线）；断电重来；换端口 |

单次尝试有 `timeout 60` 兜底，所以僵死最多浪费 60 s，不会挂死整晚。

### 3.4 (d) 第一次原子提交成功


| 项 | 期望值 | 时间窗 |
|---|---|---|
| 首帧（CRTC 已由 fbdev 起好） | `z1hwc2: first commit done (crtc already active): 240x320` | 36–120 s |
| 首帧（走完整 modeset 分支） | `z1hwc2: first commit done with modeset: 240x320` | 同上 |
| 每帧摘要 | `z1hwc2: frame <N>: device=<n> client=<none / cached / imported / copied / unusable> plane0=<used / none>` | 首帧 + 周期性（当前源码每 600 帧；中间版本是 120） |
| 纯平面兜底 | `z1hwc2: plane-only commit accepted (no modeset)` | modeset 失败后 |

判读：
- `device=0 client=copied plane0=used` = **层 A 的正常保底状态**：所有层都 CLIENT（因为 gralloc 还是 lima 的 shm（`drm_gem_shmem`），物理不连续，import 不了），client target 被 CPU 拷进 dumb buffer 后照样上屏。

- 镜像里烘的旧版 **没有** `first commit done` / `atomic commit failed` 这两条；旧版的出名日志是 `z1hwc2: <W>x<H> crtc=… planes=… layers=…`（probe 完成）和 `z1hwc2: empty crop, using full frame`。旧版提交失败时**不打印任何东西**（静默返回 `HWC2_ERROR_NONE` 以保 SF 活着）。

**FAIL 证明什么**

| 现象 | 证明 |
|---|---|
| `atomic commit failed: <errno>` | 内核拒绝了这次提交 → 按 errno 查 §4.4 |
| 一直没有 `first commit`，但服务活着 | SF 没到 present 阶段（validate/commit 序列没走完）→ 看 (e) 与 `dumpsys` |
| `first commit` 有，但 `plane0=none` 且屏幕黑 | client target 提交失败（`fb=0`：dumb 分配/拷贝失败）→ §4.6 |

### 3.5 (e) SurfaceFlinger 拿到 composer，且不再重试

```bash
# 1) SF 只启动一次（重启过就会 >1）
grep -a -c "init: starting service 'surfaceflinger'" "$Z1LOG"

# 2) "每秒等一次"应该消失（这条是 SF 阻塞在 IComposer::getService 里的证据）
grep -a "Waited one second for android.hardware.graphics.composer@2.1::IComposer/default" "$Z1LOG" | tail -3

# 3) SF 有没有被反复拉起 / 挂掉
grep -a "Service 'surfaceflinger'" "$Z1LOG" | tail -5
```

| 项 | 期望值 | 时间窗 |
|---|---|---|
| 启动 | `init: starting service 'surfaceflinger'…` **恰好 1 次** | 20–25 s |
| 等待消失 | 最后一次 `Waited one second …IComposer/default` 之后**不再出现** | ≤60 s（composer 成功后立刻停） |
| bootanim | `init: Received control message 'start' for 'bootanim' from pid: <SF pid> (/system/bin/surfaceflinger)` | 40–60 s |
| 无崩溃 | 没有 `Service 'surfaceflinger' (pid N) exited` / `signal 6 (SIGABRT)` / `z1tomb` 新增 | 全程 |

**FAIL 证明什么**

| 现象 | 证明 |
|---|---|
| `Waited one second` 一直刷到天荒地老 | composer **从未成功注册**成 `android.hardware.graphics.composer@2.1::IComposer/default`（服务在反复退出）→ 回到 (c) |
| SF 启动多次 | 有东西在 `restart surfaceflinger`：`vendor.gralloc-2-0` 的 rc 有 `onrestart restart surfaceflinger`；或者 SF 自己崩了（`eglSwapBuffers … failed`/SIGSEGV） |
| 有 `Waited one second` 但后面出现 bootanim | SF 曾经等到过（这一轮 composer 起来了），属正常，只是启动被推迟了 12 s |

> SF 在 Pie 里的行为（本地源码 `/tmp/aosp9/sf/ComposerHal.cpp:169`）：`mComposer = V2_1::IComposer::getService(serviceName);` 是**阻塞式**取服务。所以 composer 没成功之前，SF 主线程就卡在 `SurfaceFlinger::init()`，`sys.boot_completed` 永远不会置 1。**composer 一成功，SF 自己就会继续，不需要重启 SF。**

### 3.7 为什么默认看不到 `z1hwc2:` 日志（**必读**，否则会把"正常"判成"失败"）

HAL 的诊断走 `klogf()` → `open("/dev/kmsg", O_WRONLY)`。这条路上有三道门：

1. **composer 是 uid 1000（system）**。`/vendor/etc/init/android.hardware.graphics.composer@2.1-service.rc` 第 3 行 `user system`（第 4 行是 `group graphics drmrpc`）；日志里也有 `libprocessgroup: Successfully killed process cgroup uid 1000 pid 478 …`。
2. **`/dev/kmsg` 是 0644 root:root**。内核 `fork_linux/drivers/char/mem.c:719`：`[11] = { "kmsg", &kmsg_fops, 0, 0644 }`；ramdisk 的 `ueventd.rc`/`ueventd.z1.rc` **没有** `/dev/kmsg` 规则（只有 `/dev/dri/* 0666 root graphics`），所以保持内核默认。
3. **HAL 里没有任何 `ALOG*` 调用**（`z1hwc2.cpp` 只有 `#define LOG_TAG "z1hwc2"`，没有一条 `ALOGx`）⇒ 连 logcat 也不会有。

⇒ **`klogf()` 里 `open("/dev/kmsg", O_WRONLY)` 直接返回 EACCES**，代码 `if (fd < 0) return;` 静默返回，所以 `z1hwc2:` 一条都不会出现。

**解法（每开机一次；一次性、可逆、只影响本次运行）**：

```bash
Z=z1a9_gpt/scripts/z1deploy/z1push.sh
# 把 kmsg 的写权限给 graphics 组（composer 的 rc 里 group graphics drmrpc，正好命中）
$Z --rootcmd 'chown root graphics /dev/kmsg; chmod 0660 /dev/kmsg; ls -l /dev/kmsg'
# 然后重启 composer，让 klogf 重新 open 一次（fd 是进程内缓存的）
$Z --cmd 'setprop ctl.restart vendor.hwcomposer-2-1; sleep 2; getprop init.svc.vendor.hwcomposer-2-1'
$Z --cmd 'dmesg | grep z1hwc2 | tail -20'
```

> 备选：`chmod 0666 /dev/kmsg`（谁都能写，最简单，但允许任何进程伪造内核日志；调试期可接受）。
> 若想"每次开机自动生效"，需要改 ramdisk 片段（`z1a9_gpt/scripts/z1deploy/init_fragment.rc` 里加
> `on post-fs-data` + `chown root graphics /dev/kmsg` + `chmod 0660 /dev/kmsg` 后重打包）。**本次不要临时改**，用上面的在线 chmod 即可。

**兜底判据（没有 HAL 日志时怎么判 (c)(d)）**：

| 要看什么 | 不依赖 HAL 日志的证据 |
|---|---|
| composer 起来了 | `init: starting service 'vendor.hwcomposer-2-1'` 只有一次，且无 `exited with status 1` |
| composer 真的连上了 HAL | `logcat` 里**没有** `failed to open hwcomposer device` / `failed to get hwcomposer2 function N`（这两条是 HIDL 适配器打的，走 logcat → 会被 `[z1warn]` 转发到串口） |
| HAL 出过帧 | `dumpsys SurfaceFlinger` 里有 `h/w composer state:` 段（那是 `z1_dump()` 的输出）；屏幕有画面 |
| OVL 真的扫了我们的 buffer | 重跑探针 `$Z --rootcmd '/z1drmtest'`，再从 `$Z1LOG` 里看新的 plane `fb_id`（⚠️ 它会 open card1 抢 master，只在 HAL 稳定出帧后再跑；正常时客户端 target 的 dumb fb 会是一个新 id） |

## 4. 八类失败签名决策树

> 通用开头：先确认"板子是不是在跑我这一版"（§3.1 的 `z1stage:` 三行），否则下面全部无意义。

### 4.1 `failed to get hwcomposer2 function N`

```bash
grep -a "failed to get hwcomposer2 function" "$Z1LOG" | tr -d '\r' | sed 's/^\[[^]]*\] \[z1warn\] //' | sort -u | tail -5
```

- **含义**：`/vendor/lib/hw/android.hardware.graphics.composer@2.1-impl.so` 的 `initDispatch()` 在 `hwc2_device_t->getFunction(N)` 上拿到 NULL，直接放弃。**说明我们的 .so 已经被 dlopen 且 `open()` 成功了**（否则它会先打 `failed to open hwcomposer device`）。
- 历史：N=3 就是 `HWC2_FUNCTION_CREATE_VIRTUAL_DISPLAY`，上一版 HAL 的死因。
- **下一步**：
  ```bash
  Z=z1a9_gpt/scripts/z1deploy/z1push.sh
  $Z --cmd 'logcat -d -b all 2>/dev/null | grep -E "ComposerHal" | tail -5'
  $Z --cmd 'sha256sum /vendor/lib/hw/hwcomposer.z1.so /system/lib/hw/hwcomposer.z1.so'
  ```
  把 N 记下来，对照 `z1a9_gpt/scripts/z1hwc2/z1hwc2.cpp` 的 `z1_get_function()` 分支；缺了就补、重编、按 §5.2 重装。
- 顺带：**这个错误证明 (c) 的 `open` 已经通过**，别再去查 DRM。

### 4.2 `cannot open /dev/dri/card1`

```bash
grep -a "z1hwc2: cannot open /dev/dri/card1" "$Z1LOG" | tail -2
grep -a "z1hwc2: waiting for /dev/dri/card1" "$Z1LOG" | tail -2
```

- **含义**：`drm_open()` 的重试窗口内没打开节点（当前源码 `for (i=0;i<120;i++)` + 500 ms ⇒ 最长 60 s；烘进 v83test 的旧版更短）。`ENOENT/ENXIO` 会重试，其它 errno 立刻失败。
- **下一步**（shell 即可）：
  ```bash
  $Z --cmd 'ls -l /dev/dri/ 2>&1; echo ---; getprop hwc.drm.device'
  $Z --cmd 'dmesg | grep -E "mediatek-drm|Initialized mediatek|z1drm" | tail -20'
  ```
- 判读：
  - `/dev/dri/` 里没有 `card1` → (b) 失败，看 §3.2。
  - 有 `card1` 但 HAL 还是打不开 → 权限（`crw-rw-rw-` 才对）、或 `hwc.drm.device` 属性被设成了别的路径（应为空）。
  - `waited 59500 ms` 这类 → 纯粹是等太久（card1 比 60 s 还晚）→ 看 (b) 的 bind 时刻。

### 4.3 `/dev/dri/card1 has no atomic modesetting`

```bash
grep -a "has no atomic modesetting" "$Z1LOG" | tail -2
```

- **含义**：`drmSetClientCap(DRM_CLIENT_CAP_UNIVERSAL_PLANES/ATOMIC)` 失败。多半是**打开的不是 mediatek 节点**（比如通过 `hwc.drm.device` 指到了 card0 = lima，lima 是 render-only）。
- **下一步**：
  ```bash
  $Z --cmd 'getprop hwc.drm.device; ls -l /dev/dri/; cat /sys/kernel/debug/dri/1/name 2>/dev/null || echo "debugfs 未挂载"'
  ```
  期望 `hwc.drm.device` 为空（HAL 默认就是 `/dev/dri/card1`）。
- 若 debugfs 没挂（本镜像默认没挂）：`mount -t debugfs debugfs /sys/kernel/debug`（rootcmd），再 `ls /sys/kernel/debug/dri/`。

### 4.4 `atomic commit failed: <errno>`

```bash
grep -a "z1hwc2: atomic commit failed" "$Z1LOG" | tail -5
```
日志原文（当前源码）：`z1hwc2: atomic commit failed: <strerror> (flags=<0x..> planes_used=<n> device=<n> client_fb=<id> first=<0|1>)`。

| errno | 内核里真正的出处（已读源码） | 含义 | 下一步 |
|---|---|---|---|
| **EINVAL (-22)** | `drm_atomic.c:730-745`（plane 不属于该 CRTC / `drm_plane_has_format` 不支持）＋ `mtk_disp_ovl.c:381-391`（不支持的 rotation、YUV+rotation） | 格式/平面/旋转非法，或 CRTC 未启用 | 看 `z1hwc2: layer … DEVICE (… fmt=…)` 里的格式是不是 `XR24/AR24/…` 之一；把 `debug.z1.hwc.mode=0`（全 CLIENT）对照，若全 CLIENT 不报错 ⇒ 是 DEVICE 层的格式/几何问题 |
| **ERANGE (-34)** | `drm_atomic_helper.c:935-940`（**缩放**：hscale/vscale<0）＋ `drm_atomic.c:752-758`（CRTC 坐标溢出） | **src 与 dst 尺寸不等**（本板 `DRM_PLANE_NO_SCALING`），或坐标离谱 | 对比该层的 `disp frame` 与 `source crop`（dumpsys 的 `Comp Type` 表就有这两列）；层被缩放过 ⇒ policy 应该已经判 `scaling` 转 CLIENT，若漏了就修 policy |
| **ENOSPC (-28)** | `drm_atomic.c:780` / `drm_framebuffer.c:97`：**SRC_* 超出 FB 边界**（16.16 定点） | crop 大于 buffer，或 `<<16` 取整越界 | 看 `z1hwc2: layer … (src=… )` 的 crop 是否 > 缓冲尺寸；policy 的 `crop outside buffer` 会先拦，漏到这里说明 SRC 计算有 bug |
| **EACCES (-13)** | `drm_ioctl.c:701`（`MODE_ATOMIC` 带 `DRM_MASTER`）＋ `drm_ioctl.c:611-614`（`!drm_is_current_master` → `-EACCES`） | **这个 fd 不是 DRM master**（被别的进程抢走了，或 HAL 自己重开过） | 用 `$Z --cmd 'ps -A'` 看有没有 `drmtest`/`kmstest`/第二个 `composer` 在跑；杀掉占主者后 `setprop ctl.restart vendor.hwcomposer-2-1` |

补充：HAL 对**首帧**提交失败会自动降级成"纯平面提交"（不带 `ALLOW_MODESET`），成功会打 `z1hwc2: plane-only commit accepted (no modeset)`。所以看到一次失败+一次成功，是**正常的自适应**，不是故障。

### 4.5 服务每 5 秒 `exited with status 1`

```bash
grep -a "Service 'vendor.hwcomposer-2-1'" "$Z1LOG" | tail -6
grep -a -c "Service 'vendor.hwcomposer-2-1' (pid" "$Z1LOG"
```

- **含义**：HAL 进程退出码 1。两条路：`z1_open()` 返回 `-ENODEV`（DRM 打不开），或 HIDL 适配器在 `ComposerHal::init()` 里拒绝（函数表缺项 → 见 §4.1）。
- **下一步**（按顺序）：
  ```bash
  $Z --cmd 'getprop init.svc.vendor.hwcomposer-2-1'
  $Z --cmd 'logcat -d -b all 2>/dev/null | grep -E "ComposerHal|hwc" | tail -20'
  $Z --cmd 'sha256sum /vendor/lib/hw/hwcomposer.z1.so; ls -l /vendor/lib/hw/ | head'
  $Z --cmd 'dmesg | grep z1hwc2 | tail -20'     # 只有 chmod 过才有
  ```
- 注意：`exited with status 1` 出现**一次**（开机早期 card1 还没出现就退出）之后恢复正常，属于历史现象（v79 就是死在"永远退出"）。判据是**持续**每 5 s 一次，而不是"出现过一次"。

### 4.6 黑屏但 SF 是好的

判据：`init.svc.surfaceflinger=running`、没有持续 `Waited one second`、没有 `atomic commit failed`，但屏幕黑。

- **含义**：帧提交了但没有可见内容，或内容扫不出来。常见四种：
  1. 本帧**没有 CLIENT 层** → HAL 关掉 plane0（`plane0=none`）且 DEVICE 层全 import 失败 → 什么都不显示；
  2. client target 拷贝失败（`fb=0`）→ `z1hwc2: copy: … failed` / `CREATE_DUMB … failed`；
  3. 内核侧路由 B 的 DSI 没出图（`mtk-dsi … route B` 有但面板没刷新）；
  4. 画面被写到了错误的 CRTC/plane（zpos 顺序）。
- **下一步**：
  ```bash
  $Z --cmd 'dmesg | grep z1hwc2 | tail -40'
  $Z --cmd 'dmesg | grep -E "route B|mtk-dsi|mtk_dsi" | tail -10'
  $Z --cmd 'dumpsys SurfaceFlinger > /data/local/tmp/z1stage/sf.txt; wc -c /data/local/tmp/z1stage/sf.txt'
  $Z --cmd 'grep -A40 "Display 0 HWC layers" /data/local/tmp/z1stage/sf.txt'
  $Z --cmd 'grep -A30 "h/w composer state" /data/local/tmp/z1stage/sf.txt'
  ```
- 看 `Comp Type` 列：全是 `Client` 且屏幕黑 ⇒ client target 没上屏（走 2）；有 `Device` 且屏幕黑 ⇒ DEVICE 层 import/plane 编程有问题（走 1/4）。
- 历史参考：goldfish 回滚态也有过"bootanim 退出后黑屏"（`E SurfaceFlinger: Failed to remove layer from mapping`），那是老 composer 的固有问题，**不要**拿来当新 HAL 的判据。

### 4.7 `z1hwc2: client target COPIED (slow path)`（走了 CPU 拷贝兜底）

```bash
grep -a "client target COPIED" "$Z1LOG" | tail -3     # 当前源码（限速打印）
grep -a "client target copied" "$Z1LOG" | tail -3     # 中间版本源码（无节制打印）
grep -a "frame .*client=copied" "$Z1LOG" | tail -3    # 两版都有：每帧摘要里的 client=
```

- 原文（当前源码，`z1hwc2.cpp` 的 `client_target_fb()`）：
  `z1hwc2: client target COPIED (slow path): fd=<n> <W>x<H> stride=<s> fmt=<name> -> dumb fb=<id> frame=<n>`
  **打印频率有限速**：只在 `frames < 3` 和 `frames % 600 == 0` 时打 ⇒ **正常不会刷屏**。
- **烘进 v83test 的那个 .so（`e51ce536…`）没有这条日志**（`strings` 里连 `client target` 都没有），所以"看不到它"不代表没走慢路径。
- **含义**：client target 的 dma-buf **不能 import**（lima GEM 是 `drm_gem_shmem`，物理页不连续 → `mtk_gem_prime_import_sg_table()` 的连续检查失败），HAL 退回 CPU 拷贝到本地 dumb buffer。**这是层 A 的设计保底，不是故障**：屏幕应该照常显示，只是每帧多一次 240×320×4 = 300 KB 的 memcpy，且 OVL 零拷贝没有生效（`device=0`）。
- 伴随日志（当前源码）：`z1hwc2: drmPrimeFDToHandle(<fd>) failed: … (buffer is not a dma-buf, or not physically contiguous)`、validate 里 `report layer … <X> -> Client (not importable as contiguous dma-buf)`。
- **不出日志时怎么判"正在走慢路径"**：
  ```bash
  $Z --cmd 'getprop z1stage.gralloc'                       # system = 旧（lima）gralloc，必然慢路径
  $Z --cmd 'ls -l /vendor/lib/hw/gralloc.z1.so 2>/dev/null || echo "no vendor gralloc"'
  $Z --cmd 'grep -A40 "Display 0 HWC layers" /data/local/tmp/z1stage/sf.txt'   # 全是 Client 就印证
  $Z --cmd 'dmesg | grep "z1hwc2: frame" | tail -3'        # client=copied
  ```
- 注意：
  1. **不要**把 `out/z1_v83test/stage/gralloc.z1.so`（4 KB 假文件）拷进 `active/` —— 那会把 gralloc 打坏（`ELF dummy gralloc …`）。层 B 要等真正的连续内存 gralloc 构建好再做。
  2. 若你看到它**每帧**都打（说明跑的是无节流的中间版本），那是日志噪声而非新故障；把 `debug.z1.hwc.verbose` 降到 1 即可（当前源码的这条是 `level 1`，仍会打；只有回到 `verbose 0` 才完全不打印）。

### 4.8 开机挂死 / 完全没输出

**主机侧（刷写）：**

| 现象 | 动作 |
|---|---|
| 45–60 s 内没有任何新行（内核 banner 都没） | 断电 10 s 重来；确认刷写成功（§2.4） |
| LK banner 之后静止 | 内核早期 panic（`panic=10` 会重启）→ 看抓包尾部有没有 `Kernel panic`/`Unable to mount` |
| 反复重启（banner 循环） | 镜像不完整（半写/超 6 MiB 踩了 RECOVERY）→ 重新刷回 v79（§7 L2） |

**板子侧（能连上 shell 时）：**

```bash
$Z --cmd 'getprop init.svc.vendor.hwcomposer-2-1; getprop init.svc.surfaceflinger; getprop sys.boot_completed; getprop init.svc.zygote'
$Z --cmd 'dmesg | tail -40'
$Z --cmd 'ps -A 2>/dev/null | grep -E "composer|surfaceflinger|zygote"'
```

| 现象 | 证明 | 下一步 |
|---|---|---|
| composer 一直 `exited with status 1` + SF 一直 `Waited one second` | HAL 加载失败链（§4.1/4.2/4.3） | 按对应条目查 |
| composer 活着、SF 卡在 `Waited one second` | composer 没注册到 servicemanager（HIDL 服务名没出现） | 板子上跑 `logcat -d`，找 `hwcomposer` / `composer` 关键字；必要时按 §5.1 chmod 后看 HAL 日志 |
| 出现 `[z1relay] ==== DEEP DUMP begin (boot_completed after 600s) ====` | 开机 600 s 没完成，转发器在自动取证 | 看它后面的 `---- tombstone ----` / `FATAL window`，通常是 Java 侧（zygote/PMS）而不是 HAL |
| 完全没输出 + 串口无 prompt | 内核死/镜像坏 | §7 L2 回滚 |

### 5.4 重启 composer / SurfaceFlinger 的正确姿势

| 目的 | 命令（shell 用户即可，不需要 root） | 副作用 |
|---|---|---|
| 只重启 composer | `setprop ctl.restart vendor.hwcomposer-2-1` | 若 SF 已持有旧 composer 连接，SF 会拿死代理 → 黑屏，必须同时重启 SF |
| 重启 composer + SF | `setprop ctl.restart vendor.hwcomposer-2-1; sleep 1; setprop ctl.restart surfaceflinger` | **可能连带重启 zygote**（`/system/etc/init/surfaceflinger.rc` 有 `onrestart restart zygote`）→ 整个 Java 世界重启，等 1–2 分钟 |
| 换了 gralloc | `setprop ctl.restart vendor.gralloc-2-0` | 该 rc 有 `onrestart restart surfaceflinger`，SF 会被自动重启 |
| **不需要**重启 SF 的情形 | SF 还卡在 `Waited one second`（从没拿到过 composer） | composer 一成功，SF 自己就继续 |

> 为什么"换 .so 后必须重启 SF"：Pie 的 SF 在 `init()` 里只建一次 `HWComposer`（本地源码 `/tmp/aosp9/sf/SurfaceFlinger.cpp:678-682`），只有 VR 路径会重建（`:1441-1443`）；没有 composer 死亡重连。SF 阻塞在 `IComposer::getService()` 时会自己等到服务出现 —— 这是唯一"不用重启 SF"的窗口。

### 5.6 调试属性

**只有 2026-11-10 重写版读这三个属性**（镜像里烘的旧版 `e51ce536…` 一个都不读，设了也没用）：

```bash

$Z --cmd 'setprop debug.z1.hwc.mode 0'      # 0=强制全 CLIENT（对照实验）；默认 1=auto
$Z --cmd 'setprop debug.z1.hwc.fences 1'    # 需要 debugfs + sw_sync；本镜像不满足，见下
$Z --cmd 'getprop debug.z1.hwc.verbose; getprop debug.z1.hwc.mode; getprop debug.z1.hwc.fences'
```

- `verbose` / `mode` 每帧生效（`z1_validate_display()` 里读），不用重启。
- `fences` **只在 `z1_open()`→`fences_init()` 读一次**，改了必须 `setprop ctl.restart vendor.hwcomposer-2-1`。
- **`fences` 在本镜像上不可用**（两道门）：
  1. debugfs 没挂：ramdisk 的 `init.rc` 没有 `mount debugfs`，`fstab.z1` 也没有；需要 root 手动 `mount -t debugfs debugfs /sys/kernel/debug`；
  2. sw_sync 节点是 0644 root:root（`fork_linux/drivers/dma-buf/sync_debug.c:119` `debugfs_create_file_unsafe("sw_sync", 0644, …)`），composer（uid 1000）打不开；
  3. **运行内核是否含 `CONFIG_SW_SYNC` 未确认**：本机 `.config` 现在写着 `CONFIG_SW_SYNC=y`（21:47 写入，`fork_linux/vmlinux` 22:19 重编后确实有 `sw_sync_ioctl` 符号），但 **v83test 里的内核是 19:45 编的**，两者不是同一次构建。查法：`mount -t debugfs debugfs /sys/kernel/debug; ls /sys/kernel/debug/sync/`。
  ⇒ 打开它只会看到 `z1hwc2: fences requested but /sys/kernel/debug/sync/sw_sync is unavailable (…)`，然后 release fence 仍然是 -1。**本次测试保持默认 0**。

### 5.8 在线迭代的常见坑

1. **`z1push.sh` 报 `Z1LOG is not set`** → 按 §5.1 的 `export Z1LOG=$(pgrep -af '/tmp/z1cap.sh' …)` 复用现有抓包文件，注意必须是**持续追加**的那个。
2. **`--cmd` 超时 / 看不到 `_END`** → 板子 shell 卡住（有长命令在前台）。`--wait 120` 加长；或先 `pkill -f dumpsys`（board 侧）。
3. **`--rootcmd` 一直等 `###DONE`** → `z1_rootd` 没起：`$Z --cmd 'dmesg | grep z1rootd'`；没有就说明首启的 `z1stage_boot.sh` 没跑到（§3.1）。
4. **传 112 KB 的 .so 很慢** → 正常：base64 后 ~150 KB @921600 ≈ 1.6 s 净传输，加上分块 sleep 约 3–10 s。
5. **备份当前 `/vendor` 覆盖**（换新之前）：
   ```bash
   $Z --rootcmd 'cp -f /vendor/lib/hw/hwcomposer.z1.so /data/local/tmp/z1stage/hwcomposer.vendor.bak 2>/dev/null; sha256sum /data/local/tmp/z1stage/hwcomposer.vendor.bak 2>/dev/null || echo NONE'
   ```
6. **`/data` 上的工作副本不会被开机脚本覆盖**（`kept existing`）→ 想换文件必须显式 `cp -f`（`$Z` 的 `run_push` 用 `mv -f`，没问题）。

## 7. 回滚阶梯（3 级，从便宜到贵）

### L1 — 删掉 vendor HAL → goldfish HWC1（在线，10 秒，**优先用这个**）

```bash

$Z --cmd 'getprop z1stage.hwcomposer; sha256sum /system/lib/hw/hwcomposer.z1.so'
```

- **恢复什么**：`hw_get_module("hwcomposer")` 在 `/vendor/lib/hw` 找不到后回退 `/system/lib/hw/hwcomposer.z1.so`（24,660 B，sha `394ebed3…`）＝ 原厂 goldfish HWC1，由 `HWC2On1Adapter` 包装 → 就是 v78/v79 那个"能亮屏"的状态。

- **持久性**：`active/` 已清空 → 下次开机 `z1stage_boot.sh` 仍会主动删除 vendor 覆盖，自动回到这个状态。
- **内核/ramdisk 不变**：`z1stage_boot.sh`、`z1_rootd` 还在（这正是继续在线调试需要的）。

### L3 — 连 system 一起回滚（只在 system 被改过时才需要）

本次测试**不动 system 分区**：HAL 在 ramdisk/`/vendor/lib/hw`（system 分区上的目录），gralloc 走 `active/` 机制。所以 L3 只在下列情形需要：
- 有人往 `/system` 或 `/vendor` 里写了别的东西（例如手工改 build.prop、换 gralloc 真文件）；
- `/data` 的结构坏了导致开机脚本反复失败。

```bash

# 断点续写：状态文件在 /tmp/z1chunk_android_<sha12>.state；同一分区不要同时跑两个写入
```

- **恢复什么**：`/system`（含 `/vendor` 目录）回到 v35 自检版：`/system/lib/hw/hwcomposer.z1.so` = goldfish（`394ebed3…`）、`gralloc.z1.so`、`/vendor/etc/init/*.rc`、所有 HIDL 二进制全部原样。
- **代价**：943 MB、按 2.4 MB/s 读回 + 5–6 MB/s 写，实测量级 **数分钟到十几分钟**，且本板 USB 链路会断流重试。能不用就不用。
- 回滚后 `/data` 里的 `z1stage/` 仍在，但 v79 及更早的 boot.img 没有 `z1stage_boot.sh`，不会再应用 `active/`。

**一句话原则**：先 L1（10 秒，保留一切调试能力）→ 不行 L2（1 分钟，回到 v79）→ 绝不轻易 L3。

## 附录 C：已核实但容易踩的事实（含证据）

1. **`/dev/kmsg` = 0644 root:root**（`fork_linux/drivers/char/mem.c:719`），ramdisk 的 `ueventd.rc`/`ueventd.z1.rc` 无 kmsg 规则 ⇒ composer（uid 1000，见 `.../composer@2.1-service.rc` 的 `user system`）**写不进去**；HAL 也没有任何 `ALOG*`。所以 §3.7 的 chmod 是"能不能看到 HAL 日志"的开关。
   佐证：启动日志里只有 init 能打开它：`init: Opened file '/dev/kmsg', flags 1`（logd 与 health-hal 的 `file /dev/kmsg w`）。
2. **原子提交需要 DRM master**：`drm_ioctl.c:701` `DRM_IOCTL_MODE_ATOMIC … DRM_MASTER`；`drm_ioctl.c:611-614` 非 master → `-EACCES`。**但**首次 open 会隐式成为 master（`drm_auth.c:317-335` `drm_master_open()`：`if (!dev->master) drm_new_set_master()`），而 `drm_setmaster_ioctl()` 对"曾是 master 且同 tgid"放行（`drm_auth.c:225-240`），所以 **HAL 只要做"第一个打开者"就能拿到 master**；拿不到时会打 `z1hwc2: … open but not DRM master yet (Permission denied); reopening to acquire it` 并重开重试。
3. **errno 的真实语义**：EINVAL=格式/平面/旋转（`drm_atomic.c:730-745`、`mtk_disp_ovl.c:381-391`）；ERANGE=**缩放**或坐标溢出（`drm_atomic_helper.c:935-940`、`drm_atomic.c:752-758`）；ENOSPC=**SRC 越出 FB 边界**（`drm_atomic.c:780`、`drm_framebuffer.c:97`）；EACCES=**不是 master**。这四条来自本机内核源码，不是猜的。
4. **`fences` 不可用**：debugfs 未挂载（ramdisk `init.rc` 无 `mount debugfs`、`fstab.z1` 无该项）+ sw_sync 节点 0644（`drivers/dma-buf/sync_debug.c:119`）+ 运行内核**是否含 `CONFIG_SW_SYNC` 未确认**（本机 `.config` 21:47 才有该选项、vmlinux 22:19 重编后确实带 `sw_sync_ioctl`，但 v83test 的内核是 19:45 编的）。
5. **`z1drmtest` 会 open card1**（启动日志 37.06 s），可能和 HAL 抢"第一个打开者"→ HAL 的 master 重试就是为这个设计的；它不是故障。
6. **`surfaceflinger` 的 rc 有 `onrestart restart zygote`**（`/system/etc/init/surfaceflinger.rc`），`vendor.gralloc-2-0` 的 rc 有 `onrestart restart surfaceflinger`（`/vendor/etc/init/android.hardware.graphics.allocator@2.0-service.rc`），composer 的 rc 有 `on property:init.svc.surfaceflinger=stopped → restart vendor.hwcomposer-2-1`。重启服务前先想清楚连带关系（§5.4）。
7. **boot 分区几何**：`linear_start_addr = 0x2980000`、`partition_size = 0x600000`（`out/MT6572_Android_scatter.txt` 的 BOOTIMG 项；`tools/z1_flash_chunked.sh` 的分区表同值）。镜像 > 6,291,456 B 会踩到 RECOVERY。
8. **`/system` 是 rw**（`fstab.z1`: `/dev/block/mmcblk0p4 /system ext4 rw,noatime wait`），`/vendor` 是 `/system` 里的目录 ⇒ root 可热替换 `/vendor/lib/hw/*`，不需要刷 system。
