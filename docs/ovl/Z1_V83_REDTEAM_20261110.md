## 1. 首启失败模式排名

排序原则：**先排"会让你看不见"的，再排"会黑屏"的，再排"屏幕对但内容错"的**。
"首启可见性"= 在只有串口的情况下，这个故障能不能在 90 秒内被看见。

| 排名 | 失败模式 | 概率 | 首启可见性 | 一条区分证据 |
|---|---|---|---|---|
| **R1** | HAL 日志在串口上看不见（分级/通道错配） | **高（确定性）** | 直击观测 | `logcat -d -s z1hwc2` 有、串口没有 |
| **R2** | 每帧走 CPU 拷贝 + 每帧一次失败 import → 性能塌陷 + dmesg 刷屏 | **高** | 中（dmesg 速率） | `sg_table is not contiguous` 的**行/秒** |
| **R3** | composer 仍每 ~5 s 退出（6 个子因，逐一给出指纹） | 中 | **高** | init 的 start/exited 节奏 + 退出前最后一条 `ComposerHal` |
| **R4** | card1 打开成功但第一次 atomic commit 失败（errno 表） | 中 | 高（E 级可见） | 精确 errno + `dri/1/state` |
| **R5** | DRM master 被别人抢走 → 每帧 `-EACCES` | 中 | 中 | `/sys/kernel/debug/dri/1/clients` 的 master 列 |
| **R6** | fbdev 与 HAL 抢 plane 0 | **低**（多数路径不成立，见 §5 C9） | 高 | plane0 FB_ID 从我们的 fb 变回 60 |
| **R7** | 全 CLIENT → "OVL 没生效"的误判（测试设计问题） | **高** | 高 | `validate: device=0` 与 GPU/gralloc 版本 |
| **R8** | 缺层 / 层次错 / 花屏，但日志健康 | 中 | **低** | 屏幕内容 vs `dumpsys SurfaceFlinger` 的 composition 列表 |
| **R9** | SurfaceFlinger 崩/挂（契约违背） | 低 | 高 | SF 的 tombstone / `init.svc.surfaceflinger` |
| **R10** | ramdisk 改动破坏启动 | **低** | 高 | 是否停在 preloader/init 层 |
| **R11** | 读回校验通过但镜像不是要刷的那版 | **中**（已实测发生两次） | 低 | 镜像内 HAL 的版本串 |
| **R12** | "回滚到 goldfish 正常显示"不存在 | **高（事实错误）** | 高 | goldfish 的 279 条失败日志 |
| **R13** | 装的是哪份 HAL 不确定（/vendor 覆盖是 sticky 的） | 中 | 中 | `getprop z1stage.hwcomposer` + `/vendor` 的 sha |
| **R14** | CMA/内存不够（-ENOMEM） | 低 | 高 | 96 MiB CMA vs 2×300 KB dumb |

下面逐条展开。**每条都先给机制，再给"为什么是这个概率"，再给日志指纹，最后给一条区分动作。**

### R1 HAL 的诊断全静音（首启最容易踩、且会污染所有其它结论）

**机制**
- composer 服务以 **uid 1000** 运行：`/vendor/etc/init/android.hardware.graphics.composer@2.1-service.rc` 第 3–5 行 `user system` / `group graphics drmrpc` / `capabilities SYS_NICE`。【Q】
- `/dev/kmsg` 是 **0644 root:root**（内核 `drivers/char/mem.c` 的 kmsg 设备项；ramdisk 的 `ueventd.rc`/`ueventd.z1.rc` **没有** `/dev/kmsg` 规则，只有 `/dev/dri/* 0666 root graphics`）→ uid 1000 的 `open(...,O_WRONLY)` **EACCES**。【Q，ramdisk 实读】
- r5 的 `klogf()` 确实**同时**写 logcat（`__android_log_write`，`z1hwc2.cpp:83/224-275`，22:17 才加），**而且它的注释明确写"`logcat -s z1hwc2` 和串口抓包都能看到每一行"——这句话是错的**。事实：
  - 分级映射 `level 0 → ERROR`、`level 1 → INFO`、其余 `DEBUG`；r5 的默认 `g_verbose = 1`（`z1hwc2.cpp:189` 与 `prop_int("debug.z1.hwc.verbose", 1)` 的两处），所以 level 1 的行**会被发出**，但以 INFO 优先级进 logd；
  - 串口转发脚本 `/z1_klog_relay.sh` 的周期段是 `logcat -d -b main -b system -b crash -t 1200 '*:W'`（脚本第 84 行），**只转 W/E/F**；deep dump（第 44 行）只 grep `FATAL|AndroidRuntime|Process:|Exception`。⇒ **INFO 一律不进串口**；
  - r5 还给 `klogf` 加了**每秒最多 5 条**的限流（`used >= 5 → dropped++`，`z1hwc2.cpp` 的 `klogf` 内），超了只打一条 "N earlier line(s) dropped"——所以即便通道通了，**首帧的逐层诊断也可能被限流吃掉**；
  - ⇒ **HAL 的 INFO 级日志（"open … version"、"validate: layers=… device=…"、"report layer … →…"、"drmPrimeFDToHandle failed"、"drmSetMaster …"、"first commit done"）在串口上一条都看不到**；只有 E 级（`atomic commit failed…`、`copy: mmap failed…`、`cannot open …`、`layer … lost its framebuffer, skipping`）能出来。
- 如果刷的是 22:04 的 **r3**，连 logcat 通道都没有（`nm -D -u` 里没有 `__android_log_write`，只有 `open("/dev/kmsg")`）→ **HAL 完全静音**。

**概率：高（确定性）**。r3 是必然全静音；r5 是"关键行全在 INFO，被 relay 的 `*:W` 丢掉"。
**日志指纹**：串口日志里 `init:`/`mediatek-drm`/`z1drm` 都有，唯独 `z1hwc2:` 只在 E 级故障时出现；`ls -l /dev/kmsg` 显示 `crw-r--r-- root root`。
**区分动作（一条）**：用 root 通道执行
`logcat -d -s z1hwc2 | tail -n 200 > /dev/kmsg`（root 能写 kmsg）。
若这条能看到 `z1hwc2:` 而串口此前没有 → R1 成立，**之前所有"HAL 没日志"的判断全部作废，必须重判**。

> 运营建议（写进 §3 S0）：首刷前把 relay 改成 `*:I`，或让 HAL 把 level 1 映射成 WARN；否则首启等于闭眼。

### R2 每帧 CPU 拷贝（不是兜底，是首启常态）+ 每帧一次失败的 dma-buf import

**机制**
1. 扫描输出要求物理连续：`mtk_gem_prime_import_sg_table()` 在 `drm_prime_get_contiguous_size(sgt) < attach->dmabuf->size` 时 `DRM_ERROR("sg_table is not contiguous")` 并返回 `-EINVAL`（`fork_linux/drivers/gpu/drm/mediatek/mtk_gem.c:217-221`）。【Q】
2. 旧的 `/system/lib/hw/gralloc.z1.so`（18 700 B，5 月 29 日）是 **lima GEM**（`strings` 里有 `z1_lima_alloc_dmabuf`）→ 页不连续。【B】
3. 新 gralloc（镜像里 28 548 B）的后端链是 `dma_heap → card1 dumb → lima`，每次探测失败后有 **2 000 ms** 退避（`z1_heap.cpp:186-188` 注释、`kRetryIntervalMs`），**不阻塞等待**；而 `/dev/dri/card1` 到 **35.7 s** 才出现（【L】`z1drm` 37.06 s 打开、`mediatek-drm … bound` 35.68 s）。SF 在 **~20 s** 就创建了 FramebufferSurface 的 target buffer。
4. ⇒ **首启的 client target 在 card1 出现之前分配 → 落在 lima 分支 → 永远非连续**。即便 2b2 的 mknod 把 `/dev/dma_heap/default_cma_region` 建出来，它和 SF 的首次分配也是**竞态**（post-fs-data ~20.5 s vs SF ~20 s）。
5. HAL 的 `client_target_fb()` 对失败**没有负缓存**：它只在 `h->client_fb.fb_id && handle==client_target` 时命中缓存；走拷贝路径时 `client_fb.fb_id` 永远是 0，于是**每一帧**都重新 `fb_import()` → `drmPrimeFDToHandle()` → 内核 `DRM_ERROR` + sg_table 分配/释放；然后 `copy_into_dumb()` 再 `mmap` 源 dma-buf、`DMA_BUF_IOCTL_SYNC`、memcpy 240×320×4 = **307 200 B**、`munmap`。
6. 同一条 `fb_import()` 在 `validateDisplay` 里**对每个候选 DEVICE 层也会跑一次**（`z1_validate_display` 的 "only attempt the (expensive) import when…" 段），失败同样每帧一次。

**概率：高**。首启时 target 必是 lima（机制 3/4），且 HAL 无负缓存（机制 5）。
**日志/现象指纹**
- dmesg（串口一定看得到，因为 `DRM_ERROR` 是内核打印）：`mediatek-drm …: [drm] sg_table is not contiguous` **每帧 1~3 条**（client target + 每个 device 候选层），60 fps ⇒ 60~180 条/秒；
- 串口吞吐会被吃掉（921600 baud ≈ 90 KB/s，60 条/s × ~60 B ≈ 3.6 KB/s，还不至于压死，但会把有用行冲走）；
- 若把 `drm.debug` 打开，证据更硬。
**区分动作（一条）**：
`dmesg | grep -c "sg_table is not contiguous"`，隔 5 s 再数一次；**差值为 0 说明根本没在尝试导入（可能全是 CLIENT 且 validate 提前 return），差值 ≈ 帧数 × 层数 说明 R2 成立**。

### R3 composer 仍然每 ~5 s 退出（把六个子因一次列全）

先把"5 s"这件事说清楚：init 对反复退出的非 oneshot 服务按 ~5 s 节奏重启（【L】34.10/34.17、34.37/34.17、39.11/39.19、44.19… 实测间隔 4.7–5.0 s）。所以"每 5 s 退出"= 服务**加载/打开阶段**失败，还没进到 `presentDisplay`。

| 子因 | 机制（源码/证据） | 日志指纹 | 概率 |
|---|---|---|---|
| (a) 仍缺一个 descriptor | **已排除**：HIDL 适配器 `HwcHal::initDispatch()` 恰好要求 **43** 个 `HWC2_FUNCTION_*`（`/tmp/aosp9/hidl/HwcHal.h:521-585`），本地头文件的 2.1 枚举 **43 个全被 `z1_get_function()` 覆盖**（脚本对比：header 53 个 minus 10 个 2.2+/2.3+），2.2+ 走 `descriptor >= HWC2_FUNCTION_SET_LAYER_FLOAT_COLOR → nullptr`，适配器不查这些 | 不会出现 | 极低 |
| (b) `open()` 返回非 0 | `z1_open()` 只在 `drm_open() < 0` 时返回 `-ENODEV`；`drm_open()` 里 `open()` 失败且 errno∉{ENOENT,ENXIO} 立即 -1，否则 100×500 ms 重试；**拿不到 master 时关 fd 重开（250 ms）**，100 次后返回 -1。⇒ `-ENODEV` 的唯一出口是"50 s 内没能成为 master 或节点永远没出现" | `E ComposerHal: failed to open hwcomposer device: No such device`（= v79 在 34 s 的那条；因为当时卡还没出现，旧 HAL 只等 ~10 s） | 中（仅当启动时序被拖到 >50 s） |

| (d) 适配器拒绝 device version | **已排除**：`hwc2_open()` 不校验版本（`include/hardware/hwcomposer2.h` 的内联实现只转发 `methods->open`），`HwcHal` 只在 `getFunction` 返回 NULL 时失败 | 不会出现 | 极低 |

| (f) `hw_get_module` 回退到 `/system` 的 goldfish | 镜像是 rw，`/vendor/lib/hw/hwcomposer.z1.so` 只是"上一次启动留下的文件"；`/system/lib/hw/hwcomposer.z1.so`（24 660 B）是 ranchu HWC1，它要 `hw_get_module("gralloc")` 的 framebuffer HAL 才能开 fb；本 system 的 gralloc 是 lima 版，**没有可用的 framebuffer HAL** | `E hwcomposer: ranchu_hw_composer hwc_open could not open framebuffer` + `failed to open hwcomposer device: Invalid argument`（【L】279 条） | 中（取决于 M2：首启到底装不装 /vendor） |

**区分动作（一条）**：看 composer **退出前最后一条** logcat 消息：
- `failed to get hwcomposer2 function N` → (a)（已排除，若真出现说明 .so 不是镜像里那份）；
- `failed to open hwcomposer device: No such device` → (b)；
- `…: Invalid argument` 且前一条是 `ranchu_hw_composer` → (f)；
- 什么都没打、退出码 1 → 进程在 `hw_get_module`/`dlopen` 阶段死（见 R11/R13）；
- **启动了但从不退出、也没有任何 `z1hwc2:`** → 不是 R3，是 R1。

### R4 card1 打开成功，但第一次 atomic commit 失败

**机制**：`z1_present_display()` 用 `drmModeAtomicCommit(fd, req, flags, …)`，`flags` 首帧在"connector/mode/active 三属性齐全"时带 `DRM_MODE_ATOMIC_ALLOW_MODESET`，否则 0。逐 errno 的可能来源（**这是本报告对计划最有用的修正之一**）：

| errno | 本内核里真正会返回它的位置 | 本 HAL 中的触发条件 | 区分指纹 |
|---|---|---|---|
| **-EACCES** | ① `drm_ioctl.c:701` `DRM_IOCTL_MODE_ATOMIC` 带 `DRM_MASTER` 标志，非 master → `drm_ioctl_permit()` EACCES；② `drm_atomic_uapi.c:557/601` 里 `CRTC_ID` 值找不到对象（**不是**权限，是 `drm_crtc_find` 失败） | ① R5（master 丢了/被抢）；② `h->crtc_id` 错（实测 59，正常） | `dri/1/clients` 的 master 列；`h->crtc_id` 来自 getResources，不会错 |
| **-EINVAL** | ① `drm_atomic.c:1707-1717`：**需要 modeset 但 flags 没有 ALLOW_MODESET**；② 属性不属于该对象/属性 id 为 0（**22:04 前的 `MODE` vs `MODE_ID` bug 就是这种：整个 commit 直接 EINVAL**，commit `6dcb71f` 已修）；③ `CRTC_W/H==0`、blob 长度不对、`src_w==0` | ② 若 .so 是旧版（R11/R13）；③ handle 几何为 0/垃圾（R8 的表） | 打开 `/sys/module/drm/parameters/debug=0x0e` 后 dmesg 的 `[drm:…]` 行会直接说原因 |
| **-ENOSPC** | **`drm_atomic.c:780`：源矩形超出 framebuffer**（`src_x/src_w/src_y/src_h` 对 `fb->width/height`）。另一处 `drm_framebuffer.c:97` 是 legacy setplane 的同类检查 | **fb 是按 gralloc handle 的 `width/height` 建的，SRC 却取自 crop/display frame**；两者不一致（handle 布局错、或 crop 大于 fb）→ ENOSPC | 若有日志，`drm_dbg_atomic` 的 "Invalid source coordinates … (fb WxH)"；否则只能靠"plane 0 的 SRC 与 FB 尺寸对不上" |
| **-ERANGE** | `drm_atomic_helper_check_plane_state()` 的源/目标越界检查（`drm_atomic_helper.c` 内 `return -ERANGE`） | 同上（SRC 越界/负坐标），或 CRT C_X/Y 为负 | 同上 |
| **-EBUSY** | 本 HAL **不可能**：内核只在 `nonblock && 上一次 commit 未完成` 时返回（`drm_atomic_helper.c:2584/2606`），而 HAL 不设 `DRM_MODE_ATOMIC_NONBLOCK`。**唯一真 EBUSY 是 `drmSetMaster` 时 `dev->master` 已被别人持有**（`drm_auth.c:259`） | R5 | `drmSetMaster` 的 errno |
| **-ENOMEM** | atomic state / sg_table 分配失败 | 1 GB 内存 + 96 MiB CMA，基本不可能 | 内核 OOM 日志 |

**关于"ALLOW_MODESET 在已被 fbdev 配好的 CRTC 上会不会失败"**（任务点名要问的）：
- **不会因为"已经有 modeset"而失败**。ALLOW_MODESET 是**许可位**，不是请求；只有"需要 modeset 但没带这个位"才 EINVAL（上表 -EINVAL ①）。【Q】
- **它也不会主动触发 modeset**：本次 commit 只有在 `drm_mode_equal(old_crtc_mode, new_crtc_mode)==false`、或 connector/active 变化时才置 `mode_changed`（`drm_atomic_helper.c:666-673`）。HAL 的 blob 是 `connector->modes[0]` 的副本，而 fbdev 已把同一 mode 设进 CRTC ⇒ 相等 ⇒ `mode_changed=false` ⇒ **`mtk_crtc_atomic_enable()` 不会被调用**。
- **但如果两者不相等**（例如 fbdev 用的是 adjusted mode / 另一个 mode entry），就会走完整 modeset → `mtk_crtc_atomic_enable()` → `mtk_crtc_ddp_hw_init()`，而后者在结尾**强制把所有 plane 置 `pending.enable=false` 并按 CPU 路径关掉每一层**（`mtk_crtc.c:417-431`），随后重跑 mutex/clk/`ddp_comp_config`。**这才是"首帧黑一下甚至常黑"的真实机制**，且它是"mode 不等"的副作用，不是 ALLOW_MODESET 本身。
- 区分：`echo 0x0e > /sys/module/drm/parameters/debug` 后看下一帧 dmesg 有没有 `enabling [CRTC:59]` / `mode changed`；或读 `/sys/kernel/debug/dri/1/state` 的 CRTC mode 字符串。

**概率：中**。MODE_ID bug 已修（r5），剩下的 EINVAL/ENOSPC 主要来自 handle 几何与 crop 一致性（与 R8/R13 同源）。
**区分动作（一条）**：先 `echo 0x0e > /sys/module/drm/parameters/debug`（root），再做一次 present，**`dmesg` 里的 `drm_dbg_atomic` 会直接给出属性名和原因**——这是 r5 里唯一不依赖 HAL 日志的归因手段。

### R5 DRM master 被抢 → 每帧 -EACCES（计划里被低估的一条）

**机制（全部有源码行）**
- 只有 master 能提交原子请求：`drm_ioctl.c:701` `DRM_IOCTL_DEF(DRM_IOCTL_MODE_ATOMIC, drm_mode_atomic_ioctl, DRM_MASTER)`；`drm_ioctl_permit()` 对 `DRM_MASTER` 校验 `drm_is_current_master()`。【Q】
- **第一个 open 者自动成为 master**：`drm_auth.c:317-333` `drm_master_open()` 的注释就是 "if there is no current master make this fd it"。【Q】
- **后来者想抢**：`drm_setmaster_ioctl()` → `drm_master_check_perm()`：`was_master && same tgid` 才放行，否则 **必须 `capable(CAP_SYS_ADMIN)`，否则 -EACCES**（`drm_auth.c:233-243`）。composer 只有 `CAP_SYS_NICE`（rc 第 5 行）→ **一旦别人先拿到 master，composer 这一进程永远抢不回来**。【Q】
- HAL 的应对：`drm_open()` 在 `drmSetMaster()` 失败时 **close 再 open**，期望"下一次 open 时 dev->master 已空"；共 100 次、每次 250 ms。⇒ **只在"别人是短命进程"时自愈**（关掉后下个 open 拿到）；如果占用者长期活着，100 次后 `z1_open` 返回 `-ENODEV`，composer 退出，init 5 s 后重启，**循环**。
- 板上现成的竞争者：`init.z1.rc:38` 在 `post-fs-data` 用 `exec_background` 跑 **`/z1drmtest`**；它在 20.55 s 起、**等 16 s**、在 **37.06 s open `/dev/dri/card1`**、37.17 s 退出（【L】1845x 段 `z1drm: waited 16s for the KMS node` / `RESULT: PASS` / `Service 'exec 13 (/z1drmtest)' … exited`）。**它和 composer 的 500 ms 轮询是同一条赛道。**
- 当前 v83 的 `z1stage_boot.sh` 还要 `mknod /dev/dma_heap/*`、并且（若 gralloc 进 `/vendor`）gralloc 的 `card1` 后端也会 open 同一节点——**每一方都在同一个 500 ms 粒度上抢"第一个 open"**。

**概率：中**。composer 的 50 s 重试通常能在 35.7→36.2 s 抢在 z1drmtest 的 37.06 s 之前；但**只要 post-fs-data 被拖慢（R10）或 composer 首启被推迟到 36.5 s 之后**，z1drmtest 就先拿到 master，而 z1drmtest 在 37.17 s 退出后 `dev->master` 变 NULL、composer 那份 `file_priv` 仍是 `was_master=0` → **`drmSetMaster` 返回 -EACCES**，重开也拿不到（`drm_master_open` 此时会因 dev->master==NULL 而给它 master，所以"重开"这条路其实能自愈——**前提是它还有重开机会**）。这条链的每一步都能在日志里定位，见下。
**日志指纹**
- HAL 侧（r5，INFO 级，串口默认看不到，需 `logcat -s z1hwc2`）：
  `z1hwc2: /dev/dri/card1 open but not DRM master yet (Operation not permitted); reopening to acquire it`
  `z1hwc2: atomic commit failed: Permission denied (flags=0x0 …)`
- init 侧（串口可见）：`starting service 'vendor.hwcomposer-2-1'` 与 `Service … exited with status 1` 的间隔 **≈25 s 或 ≈50 s**（不是 5 s）→ 说明卡在 `z1_open` 的 master 循环里耗尽了。
**区分动作（一条）**：
`cat /sys/kernel/debug/dri/1/clients`
（`drm_debugfs.c` 输出列：`comm pid minor master auth uid magic name id`，master 列是 `y/n`）。**答案只有两种：`vendor.hwcompos y` → master 没问题，R5 排除；任何别的进程 `y` 而 composer `n` → R5 成立。**

### R6 fbdev 与 HAL 抢 plane 0（结论：**多数路径不成立**，但有两个真口子）

**机制**
- 板上 plane 0 是 PRIMARY，fbdev 已把它的 fb（**id 60**）和 CRTC（**59**）设好，`CRTC_W/H=240/320`、`SRC_W/H=0x00F00000/0x01400000`（=240/320<<16）——这是 `z1drmtest` 在 37.07 s 读出来的**实测状态**（【L】`z1drm: plane[0] id=35 crtc_id=59 fb_id=60 …`）。【L】
- fbcon 已被 `z1_fbcon_takeover.sh` 解绑：它只写 `/sys/class/vtconsole/vtcon*/bind=0`（脚本 11-35 行），**不解绑 DRM fbdev，也不释放 fb**；`z1_display_takeover.sh` 另外 mknod `/dev/tty0` 并调 `z1_bootdiag --graphics-mode`（KD_GRAPHICS）。两者都**不碰 DRM**。【Q，脚本实读】
- 唯一能让 fbdev 重新编程 plane 0 的用户态路径是 **`drm_lastclose()` → `drm_client_dev_restore(dev,false)`**（`drm_file.c:406-411`），它只在 **card1 的最后一个 fd 关闭**时触发；也就是说：**只要 composer 还开着 fd，fbdev 就不会回来抢**。
- 另一个口子是"有人写 `/dev/fb0`"：`drm_fb_helper` 的 dirty 路径会用 fb 60 重新提交 plane 0。板上确实有进程打开 `/dev/graphics/fb0`（`allocator@2.0-s`，【L】`avc: denied { ioctl } … ioctlcmd=0x4602`），但它只做 `FBIOGET_VSCREENINFO`（0x4602），**不写**。

**概率：低**。真正的风险是**反过来的**：composer 持 fd 期间 fbdev 的"安全网"是**失效**的——HAL 崩了以后如果 composer 进程还活着（比如只是 present 失败），屏幕会冻结在最后一帧 HAL 画面，而不是回到 fbdev 画面。
**日志指纹**：`/sys/kernel/debug/dri/1/state` 里 plane 0 的 `fb=` 从我们的 fb 变回 **60**；或 `dri/1/clients` 里 composer 消失、fbdev 相关的 client 出现。
**区分动作（一条）**：每次观察前后各 `grep -E "plane.*fb=" /sys/kernel/debug/dri/1/state | head -1`，比对是否为 60。

### R7 全 CLIENT：**首启可能根本测不到 OVL**（测试设计问题，不是 bug）

**机制**：`validateDisplay` 的 device 判定要求 `handle_ok && format_ok && importable && transform==0 && 完全在屏内 && src==dst`。importable 来自 `fb_import()`（连续 dma-buf）。旧 gralloc 全 lima ⇒ **所有层 CLIENT**；新 gralloc 只有在 card1 出现后新分配的 buffer 才可能是连续。
- 首帧/开机动画的层在 ~20–30 s 分配 ⇒ 无 card1 ⇒ lima ⇒ CLIENT。
- Launcher/应用层在 ~40 s 之后分配 ⇒ 可能走 dumb/CMA ⇒ 连续 ⇒ 可成 DEVICE。
- 因此**首启的 `validate` 很可能是 `device=0 client=N`**，屏幕靠 CPU 拷贝的 client target 亮着——**这完全符合设计**，却会被误读成"HAL 没生效"。

**概率：高**。**日志指纹**：`validate: layers=N device=0 client=N changes=N`（INFO 级，需 logcat）。
**区分动作（一条）**：`ls -l /vendor/lib/hw/gralloc.z1.so` + `getprop z1stage.gralloc`（`active`/`system`）。装的是 system（lima）→ 首启**不可能**有 DEVICE 层，验收标准 3 不适用。

### R8 缺层 / 层次错 / 花屏，而日志看起来健康

**机制（按可能性排序）**
1. **validate 判 DEVICE、present 导入失败 → 该层谁都不画**（静默缺层）。`z1_validate_display()` 里 import 成功（`l->fb.fb_id` 非空）→ 判 DEVICE；到了 `z1_present_display()` 又检查 `l->fb.handle != l->handle || l->fb.src_fd != fd`，不满足就 `fb_forget` 并重导；重导失败只打一条 **level 0** 的 `layer %llu lost its framebuffer, skipping`——注意它是 E 级，串口**能**看到；但 SF 不会再回来把该层改成 CLIENT（这一帧已经 present），**该层内容消失**。这是"日志看起来健康（只有一条 E）但屏幕缺一块"的最现实机制。
2. **z 序**：`zpos` 不可变且等于 plane 序号（`mtk_plane.c:340`），HAL 把 client target 固定放 plane 0、device 层按 z 升序放 1..N；`z1_policy_decide()` 保证 DEVICE 是"连续顶段"。**这套逻辑自洽**（§5 C12）。风险在"层数 > 5"时（1 target + 4 planes）：多出来的层必须降 CLIENT，policy 会做；但如果 `plane_count` 实测不是 4（比如 DSI/RDMA 也贡献了 plane），映射会整体错位。**实测是 4**（【L】`z1drm: planes: count=4`），所以这条概率低。
3. **半透明/alpha**：`program_plane()` 把 `alpha` 量化成 0..255（因为 OVL 只取低 8 位，`mtk_disp_ovl.c:543` `state->base.alpha & OVL_CON_ALPHA`）——**这条是对的**（§5 C5）。但 `blend=NONE`（`PIXEL_NONE`）配 `ignore_pixel_alpha=OVL_CONST_BLEND`（`mtk_disp_ovl.c:558`）意味着 **client target 的 alpha 通道被忽略**——对 target 是对的；对某个被误判为 DEVICE 的半透明层则会变成"直接覆盖"。
4. **`visible_region` 不参与裁剪是对的**（契约 §1.5：不能按 visibleRegion 缩平面），所以被遮挡的层不会被裁错，只是多读一些像素。
5. **滚动/转场时 SF 会把 `displayFrame` 裁到 viewport**（`Layer.cpp:551-560`）⇒ 部分出屏的层在 HAL 里被 `z1_policy_device_block_reason()` 判 `partially offscreen` → 降 CLIENT。**这是"动画时突然掉到 GPU 合成"的机制**，表现为掉帧而不是错位。

**区分动作（一条）**：同一帧里对比三处——`logcat -d -s z1hwc2`（每层 DEVICE/CLIENT + why）、`dumpsys SurfaceFlinger`（SF 认为的 composition type）、屏幕。三者不一致的那一层就是 R8。

### R9 SurfaceFlinger 崩溃 / 卡死（契约违背）

我把契约 §0 的 10 条与当前实现逐条对过（函数名级，见 §7），**大项都满足**：43/43 函数、hotplug 补发、1 个 config 且 VSYNC_PERIOD>0、三个 count 查询支持 NULL、只做 DEVICE→CLIENT、acquire fence dup+wait、0 capability、close 完整。
**剩下的真问题（都不至于让 SF 崩，但会让画面错）**：
1. **release/present fence 默认 -1**（`debug.z1.hwc.fences=0`）→ 契约 §3.2 的撕裂（SF 认为上一块 buffer 立即可写）。不崩。
2. **commit 失败时 `presentDisplay` 返回 `HWC2_ERROR_NONE`**（"keep SurfaceFlinger alive"）→ SF 认为这一帧成功了，用 -1 的 release fence 放掉缓冲区 → 下一帧可能读到正在写的 buffer。不崩。
3. **CLIENT 层的 acquire fence 只 dup 不消费**：`z1_set_layer_buffer()` 对**所有**层 `dup(acquire_fence)`；`z1_present_display()` 只 wait/close **DEVICE** 层的。⇒ 一个层一旦稳定为 CLIENT 且不再收到 `setLayerBuffer`，它那份 dup 的 fd 就**挂着不关**（一个层一个 fd，不是每帧增长）。不崩，但属于资源泄漏。
4. **`presentOrValidate` 路径**：SF 在没有 client composition 时走 `presentOrValidate`；HAL 没有 advertise SKIP_VALIDATE，命令引擎会先 present 再 fallback validate（`ComposerCommandEngine.h:271-310`）。也就是说**同一帧可能先被 present 一次（没有 validate）**——HAL 的 `presentDisplay` **不检查 `h->validated`**，会用上一帧的 `h->layers[].composition` 直接提交。首帧时 `validated=false`，若 SF 走 present-or-validate，HAL 会用全 INVALID 的层状态提交一次（每个 INVALID 层都不在 device_layers 里 ⇒ 只提交 client target ⇒ 屏幕只显示 target，一层不画）。**这是"首帧缺层"的第二个机制**，且和 R8-1 不同：它是**协议层**的。不崩，但会闪一帧。
5. `get_release_fences()` 在 `(NULL,NULL)` 查询时返回 `layers.size()`，填充时对**所有**层（含 CLIENT）返回 `-1` 或真 fence——规格允许，SF 丢弃无效 fence。不崩。

**概率：低**。**区分动作（一条）**：`getprop init.svc.surfaceflinger` + `/data/tombstones/` 有没有新增（`z1_klog_relay.sh` 的 deep dump 会在 boot_completed+45 s 抓）。

3. 板上实测就是失败：**279 条** `ranchu_hw_composer hwc_open could not open framebuffer`，紧随 `failed to open hwcomposer device: Invalid argument`（【L】18791、18799、18949、18968、19007…），**没有一次成功**。
4. `/system/vendor/lib/hw/hwcomposer.z1.so` 在 system 镜像里**不存在**（`ls` 实测）——`/vendor/lib/hw/…` 这份覆盖只能由 **ramdisk 的 cp / stage 脚本**创建，**且它会跨刷机保留在 rw 的 /system 上**。【B】
⇒ "刷上一版 boot.img"只会：上一版 ramdisk 的 `init.z1.rc:42` 再 cp 一个旧 HAL 进 /vendor（v79 ramdisk 里那份 109 KB、缺 CREATE_VIRTUAL_DISPLAY）；它**不会**回到 goldfish。要回到 goldfish 必须 `rm /vendor/lib/hw/hwcomposer.z1.so`，而它**也打不开 fb**。
**结论**：首启**没有**"已知可用的 combiner"可回滚，只有"静态 fbdev 画面"这一种已知状态。计划 §R6 与 runbook §0.2 的 fail-safe 前提必须改写。

### R13 装的是哪份 HAL：/vendor 覆盖是 sticky 的

**机制**：`hw_get_module("hwcomposer")` 按 `<variant>=z1` 搜 `/odm/lib/hw → /vendor/lib/hw → /system/lib/hw`，**找到第一个能 `dlopen` 的就停**；`/vendor` 那份是 rw 分区上的普通文件，**不会随 /system 镜像回滚**。所以：
- 首启 `apply` 装 r5 → 下次启动若 `active/` 被清空 → `apply` 会**删掉**它（脚本确实删）；
- 但若脚本没跑到（/data 坏、`exec` 被杀、`/vendor` ro）→ r5 会**一直**被加载；
- 若 r5 的 `dlopen` 失败（缺符号/依赖）→ libhardware **静默回退**到 `/system` 的 goldfish → 表现为 R3(f)，**不是** "HAL 没装"。
**日志指纹**：`getprop z1stage.hwcomposer`（脚本 3 段 `set_prop "$_prop" active|system`，`_prop = "z1stage.hwcomposer"`）；**磁盘 sha**：`sha256sum /vendor/lib/hw/hwcomposer.z1.so`。
**区分动作（一条）**：这三者一起抓——`getprop z1stage.hwcomposer`、`sha256sum /vendor/…`、`logcat -s z1hwc2 | grep version`（r5 的启动行会打版本串；r3 不会打任何东西）。

### R14 内存/CMA：低

96 MiB CMA 池（【L】`Reserved memory: created CMA memory pool at 0x9a000000, size 96 MiB`），dumb shadow 2×307 200 B，client target 的 target buffer 300 KB/块。**不可能 -ENOMEM**。唯一相关的失败是 `/dev/dma_heap` 缺失（计划"更正 4"）——现在的脚本用 mknod 补（2b2 段），但**成败取决于内核的 `sys/class/dma_heap/default_cma_region` 是否真的存在**；如果没有，gralloc 落 lima，回到 R2。

## 2. 对计划本身的反对（每条：反对点 + 证据 + 我改怎么做）

> 规则：只反对机制，不反对人；**每条都给一个可执行的替代**。

### O1 首启同时改 HWC **和** gralloc = 两变量实验，失败不可归因
- **反对**：镜像里的 `z1stage_boot.sh` 在 2b 段对 `hwcomposer.z1.so` **和** `gralloc.z1.so` 都做 `auto_once`（`AUTO_ONCE_HWC/AUTO_ONCE_GRALLOC`），而 `apply` 在末尾把它们装进 `/vendor/lib/hw`。计划文本说层 B（gralloc）是后续步骤——**镜像和计划不是一回事**。
- **证据**：§0.1/§0.3 M1；脚本 2b 段 + `auto_once hwcomposer.z1.so hwc AUTO_ONCE_HWC` / `auto_once gralloc.z1.so gralloc AUTO_ONCE_GRALLOC`。
- **替代**：首刷只 auto_once **HWC**；gralloc 留成"候选"（seed 到 `/data/local/tmp/z1stage/gralloc.z1.so`），由 `z1_install_hal.sh` 在线装。首启若花屏/黑屏，第一件事就是把它删掉回 stock。

### O2 观测通道没有设计：先修可观测，再谈首启
- **反对**：r3 全静音；r5 的 INFO 被 relay 的 `*:W` 丢掉。**首启的验收标准 1/3/4 全部依赖"能看到 HAL 的话"，而现在看不到。**
- **证据**：R1（kmsg 0644 root:root + composer uid 1000；relay `*:W`）。
- **替代**（三选一，按成本从低到高）：
  1. 串口侧命令：`logcat -d -s z1hwc2`（root daemon 执行，输出写 `/dev/kmsg`）——**零改动，首启就能用**；
  2. 把 relay 改成 `*:I`（只改一个脚本，但日志量 +）；
  3. HAL 里把 level 1 映射成 `Z1_LOG_WARN`（改一行，需重打镜像）。
  **我选 1**，并把它写进 §4 的必抓项。

### O3 "CPU 拷贝兜底"其实是首启主路径：要么接受它，要么先解决 target 的分配时序
- **反对**：计划把 copy 当"失败兜底"；实际是"首启每次都会走"，因为 SF 在 card1 出现前就分配 target。计划没有给出"什么时候 target 会变连续"的判据。
- **证据**：R2 机制 3/4；`z1_heap.cpp` 的 2000 ms 退避（不阻塞等待）；`mediatek-drm … bound` 35.68 s vs SF 启动 19.6 s。
- **替代**：
  (a) 给 `fb_import` 加**负缓存**（key = `(handle, fd)`，失败只记一次，直到 handle 变化）——省掉每帧的内核 DRM_ERROR 与 sg_table 抖动；
  (b) 把"client target 的连续性"作为**显式验收项**：`cat /sys/kernel/debug/dri/1/state` 看 plane0 的 FB 是不是我们的 dumb（拷贝路径）还是 import 的（零拷贝）；不要靠"屏幕亮不亮"判断；
  (c) 若要零拷贝 target：让 gralloc 对 `GRALLOC_USAGE_HW_FB` **阻塞等待 card1**（带超时）或用 mknod+CMA 抢在 SF 之前——但那是层 B 的活，别塞进首启。

### O4 50 s 阻塞 `open()` 的代价被低估了：它把"启动顺序"变成了"master 竞争的胜负手"
- **反对**：计划把"等 card1 50 s"说成优点。它确实必要（35.7 s 才出现），但它让 composer 的主线程/SF 的 `ComposerHal::init()` 悬置 ~16 s，并且把"composer 何时 open"变成 R5 的胜负手。计划没有把 z1drmtest 移出这条赛道。
- **先回答"会不会触发 init 超时"（任务点名）**：**不会**。A9 的 init 对普通 service 在 `fork+exec` 成功后就认为"started"（日志 `starting service 'vendor.hwcomposer-2-1'...`），它不等子进程进入 HIDL 注册循环；本项目也没有设 `ro.service_start_timeout`（`init.rc`/`init.z1.rc` 里 grep 无）。50 s 的 `open()` 发生在 **composer 进程的 `main()` 里**，所以被拖住的是：
  (a) composer 自己（16 s 后才 `registerAsService`）；
  (b) **SurfaceFlinger 的主线程**（`ComposerHal::init()` → `hw_get_module()` → 我们的 `z1_open()`，同步 16 s）——开机时间 +16 s，但不致命；
  (c) **真正的代价**：composer 的 open 时刻落在 35.7–36.2 s 这个窗口，而 `/z1drmtest` 在 37.06 s 抢同一个"第一个 open"（R5）。
  对比：如果这是 `exec`（像 `init.z1.rc:42` 的 cp 那样），才会有 init 侧的超时/阻塞问题；而 `exec` 的那条路（stage 脚本）已经通过"脚本必须 <2 s"约束住了（R10）。
- **证据**：R5；`init.z1.rc:38` 的 `/z1drmtest`（20.55 s 起，37.06 s open card1）；`/tmp/rd79/init.rc:673` `class_start hal`。
- **替代**：
  (a) **把 `/z1drmtest` 从 `post-fs-data` 删掉**（它只是诊断；v83 已经有 root 通道，可以按需跑）；
  (b) `drm_open()` 里在 `drmSetMaster` 失败后**不要**立刻 close 重开（重开抢不到 master，只会把 `was_master` 洗掉），而是**保留 fd 继续等**，并在**第一次 commit 收到 EACCES 时**再走"close/reopen 抢 master"；
  (c) 给 `drm_open()` 加一条"只要拿到 master 就打一条 ERROR 级别的日志"（这样串口一定看得到，绕开 R1）。

### O5 回滚方案不成立（R12）：先定义"可回滚到什么"
- **反对**：计划的安全网是"刷上一版 boot.img 恢复 goldfish 显示"。证据表明 goldfish 在这套 system 上**打不开 framebuffer**，且 `/vendor` 覆盖会跨刷机存活。
- **替代**：
  (a) 把回滚定义成**三条命令**（root daemon）：`rm -f /vendor/lib/hw/hwcomposer.z1.so`、`rm -f /vendor/lib/hw/gralloc.z1.so`、`reboot`；
  (b) 首刷前先把这三条写进 `/data/local/tmp/z1stage/cmd.sh` 的注释/脚本，**用串口就能触发**，不依赖"还能刷机"；
  (c) 接受"已知可用显示 = 当前静态 fbdev 画面"，不要承诺更多。

### O6 z1kmstest 与 composer 抢 master：工具的位置错了
- **反对**：`/z1drmtest` 在 init 里跑，天然和 composer 抢第一个 open。新的 `z1kmstest` 也在 ramdisk，且计划让它在首启后跑——若它先 open，它成 master；若它**只读**（不 master）没事，但它若调 `drmSetMaster` 会 -EBUSY。
- **证据**：R5；`z1kmstest` 动态依赖只有 libdl/libc（自包含），`nm` 里可见 `drmSetMaster/drmDropMaster/drmIsMaster` 的 PLT 项。
- **替代**：所有 DRM 工具**只在 composer stop 之后**跑（root daemon 脚本里先 `setprop ctl.stop vendor.hwcomposer-2-1`，跑完 `start`），并且工具自身在退出前 `drmDropMaster`。

### O7 没有"这份 HAL 是哪个版本"的板上证据
- **反对**：`rw` 的 `/vendor` + 三种安装路径（legacy cp / auto_once / operator active/）+ 一个会被删的 active/ ⇒ "现在跑的是哪份"完全靠人记。计划没有把这个变成板上可读的状态。
- **替代**：`z1stage_boot.sh` 已经在写 `z1stage.hwcomposer=active|system`；**再加一条**把 `/vendor/lib/hw/hwcomposer.z1.so` 的 sha256 写成 `z1stage.hwcomposer.sha`（`setprop` 长度够 64 hex），首启 90 秒里 `getprop` 就能确认。

### O8 计划把 "vermagic 不变 ⇒ 现有 .ko 不受影响" 说对了，但没验证 SW_SYNC 真的进了内核
- **反对**：这类"配置改了但产物没重编"的错在项目历史上出现过（v13 那次的教训）。计划只断言"同一 zImage + SW_SYNC"。
- **证据**：本次已交叉验证——`nm vmlinux | grep sw_sync` 有 `sw_sync_debugfs_open/sw_sync_ioctl/sync_timeline_*`；`.config` mtime 21:47:44 < `vmlinux` 21:48:06 < `zImage` 21:48:13；镜像内 zImage sha == 当前 zImage sha。**这条没问题**（§5 C10）。
- **替代**：把这条验证写进 packer 的检查（包 `zImage` 前 `grep -q " T sw_sync_ioctl$" System.map`），别靠人记。

### O9 计划没有覆盖 "present 时层被跳过" 的语义（R8-1）
- **反对**：validate 判 DEVICE 后，present 若 import 失败会 `continue`（跳过该层），**没有任何机制让 SF 把该层改回 CLIENT**。这是常量级的"缺层"风险。
- **替代**：present 发现某层 import 失败时，**设一个 `dirty_types` 标志**，下一次 `validateDisplay` 无条件把该层报成 CLIENT（哪怕 SF 请求 DEVICE）；同时把这条日志提到 level 0。

### O10 "首启干脆不带 vendor HAL，全靠 root 通道在线装" —— 我认为在**当前状态下**这才是对的
- **反对**：计划坚持"一次刷机就把新 HAL 带上去跑首启"。但本次审查已经证明：**镜像在 18 分钟里换了三版 HAL（r3→r4→r5）、文档还停在 r2/r3、首启脚本的语义在 runbook 里写反了**（§0.3 M1/M2）。在这种"artifact 还在动"的状态下，首启带 HAL 等于**用一个不可复现的二进制去赌第一次印象**。
- **替代（更慢但可归因）**：
  1. 首刷的 ramdisk **只带** 内核（SW_SYNC）+ root daemon + stage 脚本；把 `init.z1.rc:42` 的 legacy `cp /hwcomposer.z1.so` 与 `auto_once hwcomposer` **都去掉**（`apply` 会把 `/vendor` 里残留的旧 HAL 删掉 → 落到 stock，而 stock 的效果已知：composer 5 s 退、屏幕维持 fbdev 静态画面——**与今天完全一致，没有任何新变量**）。
  2. 首启只验证"系统起得来 + root 通道能用 + `dri/1/clients` 与 `state` 抓得到"。
  3. 然后用 `active/hwcomposer.z1.so` + `reboot` 装第一版 HAL（S4/S5）。
- **代价**：多一次 reboot（不是物理断电），少一次"首启就能出 OVL"的机会。
- **什么时候我不选它**：如果刷机前能把 artifact **冻结**（§0.1 的四个 sha 都记下、`pack_boot_report` 与镜像一致、工作树 clean + tag），那么"首启带 HWC（不带 gralloc）"是更好的选择——一次物理动作拿到更多信息。**判据就是"能不能冻结"，不是偏好。**

## 3. "最小安全首刷"：只改必须改的，一次只动一个变量

> 目标函数：**"永远不丢显示 + 每次实验最多一次物理断电"**。
> 现实前提（R12）：现在已经没有"能出 UI 的 combiner"；所以"不丢显示"的准确含义是**"不把当前静态 fbdev 画面弄坏、且每次都能用串口把系统救回来"**。

### S0（刷前，10 分钟，全部只读/本机）
1. **冻结身份**：`sha256sum out/z1_v83/boot.img`，并**从镜像里**解出 `hwcomposer.z1.so` 的版本串（§7 的一段 python），把 `镜像 sha + HAL 版本串 + gralloc sha + z1stage sha` 写进一张纸/一个文件。
2. **对齐文档**：`pack_boot_report.txt` 的 `image sha256` 必须等于第 1 步；不等 → **不要刷**，重打。
3. **改一处 relay**：把 `/z1_klog_relay.sh` 的 `*:W` 改成 `*:I`（或首启后手动 `logcat -d -s z1hwc2`）。不做这一步，首启等于闭眼（O2）。
4. **把回滚三条命令写进 `/data/local/tmp/z1stage/cmd.sh`**（O5），并确认串口 shell 能跑 `cat cmd.sh`。
5. **决定首启装不装 gralloc**：我建议**不装**（O1）。做法：在镜像里把 `auto_once gralloc.z1.so gralloc AUTO_ONCE_GRALLOC` 注释掉，或让 `active/gralloc.z1.so` 保持空。**否则首启是两个变量。**

### S1 首刷（唯一一次物理操作）
- 刷 `out/z1_v83/boot.img`（**先**确认 §2.2 的 zImage/dtb 显式参数，别看默认值）。
- 刷完**不要**动 USB 以外的任何东西；按 §4 抓 90 秒。
- **判据**：`init: starting service 'vendor.hwcomposer-2-1'` 出现后 **≥60 s 不再出现 `exited`**（说明没在 R3/R5 里循环）。

### S2 内核/DRM 侧验证（不需要换 HAL）
在 composer 还在跑的情况下也能做（只读）：
```
cat /sys/kernel/debug/dri/1/clients          # 谁 master
cat /sys/kernel/debug/dri/1/state | head -40 # plane0 fb 是不是 60 / 我们的 fb
dmesg | grep -c "sg_table is not contiguous"
```
**判据**：`clients` 里 composer 是 `master=y`；`state` 里 plane0 的 fb 已经**不是 60**（说明我们的 commit 落地过）。
若还是 60 → HAL 的 commit 没生效，进 §4 的 (c)/(d) 分支。

### S3 独立证明 atomic 可用（不经过 HAL）
```
setprop ctl.stop vendor.hwcomposer-2-1        # 先让 composer 让出 card1
/system/bin/z1kmstest probe                   # 只读探测
/system/bin/z1kmstest run --layers 1 --timeout 3000   # 真提交（它自己拿 master）
setprop ctl.start vendor.hwcomposer-2-1
```
**判据**：`run` 的退出码 0 且 `dmesg` 无 atomic 错误 ⇒ **"内核/OVL 不会编程"这个可能性被彻底排除**；之后任何显示错误都只可能来自 HAL/gralloc/SF。
**失败则**：把 `/sys/module/drm/parameters/debug` 设 `0x0e` 重跑，日志里的 `drm_dbg_atomic` 行会直接给出 errno 原因（§R4）。

### S4 用 root 通道在线换 HAL（一次重启以内）
```
# 1) 只在 active/ 里放一份，然后重启让 stage 脚本装（推荐，顺序确定）
cp /data/local/tmp/z1stage/hwcomposer.z1.so  /data/local/tmp/z1stage/active/hwcomposer.z1.so
# 2) 强制 client 模式先跑（只验证 validate + target 拷贝，不碰 OVL 层）
setprop debug.z1.hwc.mode 0
reboot            # 用 root daemon 触发，不是物理断电
```
**判据**：起来后 `logcat -s z1hwc2` 有 `version 2026-11-10-r5`；`validate: device=0 client=N`；屏幕**保持有画面**。
**失败则**：`rm active/hwcomposer.z1.so` + `reboot` → 下一次启动自动回 stock（脚本的 auto_once 语义）。

### S5 逐层打开 DEVICE（仍然一次一个变量）
```
setprop debug.z1.hwc.mode 1       # 允许 DEVICE
# 先确认 /vendor/lib/hw/gralloc.z1.so 不存在（吃 stock lima ⇒ 只可能全 CLIENT）
```
- 若 `device=0` → 不是故障（R7），是 gralloc；继续 S6。
- 若 `device>0` 且屏幕**缺层/错层** → 按 R8 定位（三处对比）。
- 若屏幕**黑**且 plane0 FB_ID=0 → 首帧无 target 的路径（§1 R8-4 / R9-4）。

### S6 最后才装 gralloc（层 B）
```
cp /data/local/tmp/z1stage/gralloc.z1.so /data/local/tmp/z1stage/active/gralloc.z1.so
reboot
```
- 装完**必须重启**：SF 的 target 在下次启动时仍会早于 card1 分配，所以**别期待 client target 变连续**；期待的是 **app 层**变连续（40 s 之后分配的）。
- 判据：`dmesg` 的 `sg_table is not contiguous` 速率**下降**（device 层不再尝试导入失败），同时 `dumpsys SurfaceFlinger` 出现 Device。
- 失败：`rm active/gralloc.z1.so` + `reboot`。

**这个顺序的性质**：S1 是唯一一次物理动作；S2/S3 只读；S4~S6 每次都是"一次 reboot 改一个变量"，且每次都有 `rm active/… + reboot` 的确定性回滚。

## 4. 首启 90 秒必须抓的五件事

> 前提：串口 921600 已在抓（`z1_capture_mainline.sh`），root 通道已起（`z1stage: done` 之后）。
> 顺序按"先抓会消失的，再抓可重放的"。

**1. 身份（30 秒内，不抓就永远说不清）**
```
getprop z1stage.hwcomposer ; getprop z1stage.gralloc
sha256sum /vendor/lib/hw/hwcomposer.z1.so /system/lib/hw/hwcomposer.z1.so
logcat -d -s z1hwc2 | head -5          # 有 version 行 = r5；没有 = r3/未加载
[dmesg | grep -a "z1stage:"]            # begin@…s / done@…s / auto-install …
```
> 为什么第一：**其余四项的解释全部取决于"跑的是哪份 .so"**；`/vendor` 覆盖是 sticky 的（R13），刷机后也可能还是旧的。

**2. composer 的生死节奏（决定 R3/R5）**
```
dmesg | grep -aE "vendor.hwcomposer-2-1|ComposerHal|hwcomposer:" | tail -30
getprop init.svc.vendor.hwcomposer-2-1
```
> 判读：`started`→`exited` **5 s** = 加载期失败（R3）；**≈25/50 s** = master 循环耗尽（R5）；**从不 exited** = 活着（继续抓 3/4/5）。

**3. 谁持有 card1、谁有 master（R5 的唯一裁决）**
```
cat /sys/kernel/debug/dri/1/clients
ls -l /proc/$(pidof android.hardware.graphics.composer@2.1-service)/fd 2>/dev/null | grep -c card1
```
> 判读：composer 行 `master=y` → 正常；别的进程 `master=y` → R5；composer 不在列表 → 它没开 card1（R3-b）。

**4. 第一帧有没有真的打到 OVL 上（R2/R4/R6）**
```
cat /sys/kernel/debug/dri/1/state | sed -n '1,30p'     # plane0 的 fb / crtc / src
dmesg | grep -ac "sg_table is not contiguous" ; sleep 5 ; dmesg | grep -ac "sg_table is not contiguous"
dmesg | grep -aE "drm_dbg_atomic|Invalid source coordinates|requires full modeset|enabling \[CRTC"
```
> 判读：plane0 的 fb **≠60** 且稳定 = 我们的 commit 在跑；`sg_table` 计数**每 5 s 涨约 帧×层数** = copy 路径（R2）；`requires full modeset` = 首帧触发了 modeset（R4 的"mode 不等"分支）。

**5. HAL 自己的话（O2；不要依赖 relay）**
```
logcat -d -s z1hwc2 | tail -n 200 > /dev/kmsg
```
> 若这条有内容而串口此前没有 → R1 确认；把**最后 200 行**留在串口日志里，下一轮才有东西可读。
> 若这条也是空并且 `/dev/kmsg` 是 0644 root:root → 说明刷的是 r3（无 logcat）或 HAL 根本没加载（R3/R13）。

## 6. 未确认事项（以及它会让哪些结论失效）

1. **`/dev/kmsg` 在板上的真实 mode**（我按内核默认 0644 推论；runbook 也引 `drivers/char/mem.c`）。
   → 若实际是 0666/0660+log，R1 的"全静音"不成立，r5 的 INFO 仍会被 relay `*:W` 丢掉（那一半仍成立）。
2. **首启到底装 HWC 还是回退 goldfish**：我按 22:22 镜像里的 `z1stage_boot.sh`（`auto_once` 在 `apply` 之前，且 apply 在末尾）判定"装 r5"。22:04 那版的脚本（sha `2062ec86`）**在 git 里不存在**，其语义不可复现。
   → 若实际是"删 /vendor → goldfish"，则首启**测的是 goldfish**，而 goldfish 按【L】是坏的 → 首启=无 composer，与今天相同。
3. **新 gralloc 的 `drm-dumb` 后端在 card1 上能否成功 `CREATE_DUMB` + `PRIME_HANDLE_TO_FD`**（不需要 master，理论上可以）。
   → 不能的话，40 s 后的层仍是 lima，`device` 永远 0（R7）。
4. **mknod `/dev/dma_heap/default_cma_region` 的 major:minor 是否正确**（脚本 2b2 从 `/sys/class/dma_heap/…/dev` 读）。
   → 不对的话 CMA 后端永远不可用，target 永远 copy（R2）。
5. **SF 在 composer 进程死亡后是否重连**（A9 `ComposerHal` 无死信处理；未见实测）。
   → 影响"在线换 HAL 不重启 SF"是否可行；我在 §3 里选了"整机 reboot"，绕开这个不确定性。
6. **`presentOrValidate` 在这块板上的实际调用序列**（SF 用 `hasClientComposition` 决定走哪条；首帧未知）。
   → 决定 R9-4「首帧缺层」是否会发生。

## 8. 一句话结论

**这个首启最可能的失败不是"HAL 写错了"，而是"你看不见它、也说不清首启测的是哪一版"**：镜像里的 HAL 是 r5、文档描述的是 r3/r2 时代的行为、`/vendor` 覆盖是 sticky 的、首启同时装 HWC+gralloc、而串口只转发 W/E/F 且 `/dev/kmsg` 对 composer 是只读不可写。
在把"身份（R11/R13）"和"可观测（R1/O2）"两件事做完之前，**任何"首启黑屏/没日志"的结论都不可信**，也不该据此改 HAL。
