## 0. 一句话

内核显示链路已经通了；**"满血 OVL"缺的不是内核，而是一个真正能被 HIDL 组合器接受的 HWC2 HAL**，
以及**能被 OVL 扫描输出的连续内存 buffer**。本轮把这两件事都做完，并且建立**串口 root 通道**，
让后面所有迭代都不再需要刷机。

## 1. 对交接文档的更正（重要）

### 更正 1：`z1_open()` 的 ENODEV 不是当前的阻塞点
交接文档 §5 说"卡在 `drm_open()` 失败（ENODEV）"。**错的。** 本轮逐行读启动日志
（`mainline_recon/z1_boot_20261109_1838.log`，最后一次启动从 63309 行开始）得到真实时间线：

| 时刻 | 日志 | 含义 |
|---|---|---|
| 23.99 s | `init: starting service 'vendor.hwcomposer-2-1'` | 组合器服务启动 |
| 32.3 s / 34.3 s | `E ComposerHal: failed to open hwcomposer device: No such device` ×2 | 此刻 `/dev/dri/card1` 还不存在（mediatek-drm 35.6 s 才 bind）→ 我们的 `z1_open()` 返回 `-ENODEV` |
| **35.68 s** | `mediatek-drm ... bound 14007000.ovl / 14008000.rdma / 1400c000.dsi` | KMS 节点出现 |
| **39.2 s 起** | `E ComposerHal: failed to get hwcomposer2 function 3`（此后 928 次） | `open()` **成功了**，是 HIDL passthrough 实现拿不到 `HWC2_FUNCTION_CREATE_VIRTUAL_DISPLAY`（=3）而放弃 |

⇒ **真正的阻塞点是我们的 `z1_get_function()` 函数表缺项**，不是 DRM 打不开。
证据：错误文本从 "failed to open hwcomposer device" 变成 "failed to get hwcomposer2 function 3"，
且该文本位于 `/vendor/lib/hw/android.hardware.graphics.composer@2.1-impl.so`（`strings -t x` 偏移 0xfe66），
是我们 .so **成功 open 之后**才可能打印的。

### 更正 2：v79 的显示其实没有工作
`vendor.hwcomposer-2-1` 每 5 秒退出一次（实测 1600 s 时仍在退），
PID 487 一直打印 `ServiceManagement: Waited one second for android.hardware.graphics.composer@2.1::IComposer/default`
= **SurfaceFlinger 从未拿到组合器**，所以它没有出帧。屏幕上是内核 fbdev/RDMA 的残留画面。
（v78 的"显示正常"是原厂 HWC1 路径，那版确实正常。）

### 更正 3：HWC2 头文件版本
`z1a9_gpt/scripts/z1hwc2/include/hardware/hwcomposer2.h` 是 Android 11 级别的头（含 2.2/2.3/2.4 函数），
但 **2.1 部分的枚举值与顺序没变**（新函数追加在尾部），所以可以用；我们实现的函数表只取 2.1 语义即可。

### 更正 4：/dev/dma_heap 当前不存在
`CONFIG_DMABUF_HEAPS{,_SYSTEM,_CMA}=y`、dts 有 96 MiB `linux,cma-default` 池，
但板上 `ls /dev/dma_heap/` = `No such file or directory`。→ 需要在 ueventd 规则/时序上补，或走 `/dev/dri/card1` dumb buffer。

## 2. 目标与验收标准

**目标（满血 OVL）**：SurfaceFlinger 把应用图层以 `HWC2_COMPOSITION_DEVICE` 交给 HWC，
HWC 用 DRM atomic 直接把这几个图层的 buffer 编到 MT6572 OVL 的 4 个硬件层上（零拷贝），
GPU 只画真正需要合成的部分（客户端合成目标那一层）。

**验收（每条都要有板上证据）**
1. `vendor.hwcomposer-2-1` 服务**稳定运行不退出**；`getFunction` 全部成功（我们的 klog 可见）。
2. SurfaceFlinger 只启动 1 次、0 崩溃、`sys.boot_completed=1`，屏幕有正常 UI。
3. `dumpsys SurfaceFlinger` 里出现 **Device composition**（至少 1 个图层 non-CLIENT）；
   我们的 HAL 日志打印每个图层的 `z/size/format/结论`，与 dumpsys 对得上。
4. OVL 寄存器/DRM 状态可证：`/sys/kernel/debug/dri/1/state` 或我们的 `z1kmstest probe`（本内核无 debugfs state，则用 plane FB_ID 读回）。
5. 回滚可验证：删 `/vendor/lib/hw/hwcomposer.z1.so` → 恢复原厂 HWC1 路径 → 显示正常。

## 3. 已核实的关键技术事实（本轮读源码/实测）

### 3.1 内核 OVL 能力（`fork_linux/drivers/gpu/drm/mediatek/`）
| # | 事实 | 证据 |
|---|---|---|
| 1 | 4 个 plane，全部来自 OVL，zpos **不可变**，plane 顺序即合成顺序 | `mtk_crtc.c` `mtk_crtc_num_comp_planes()`/`mtk_crtc_plane_type()`；`mtk_plane.c:340` `drm_plane_create_zpos_immutable_property` |
| 2 | **支持每层位置**：`pending.x/y = dst.x1/y1`，OVL 写 `(y<<16)|x` 到 `DISP_REG_OVL_OFFSET(idx)` | `mtk_plane.c` `mtk_plane_update_new_state()`；`mtk_disp_ovl.c` `mtk_ovl_layer_config()` |
| 3 | **禁止缩放**：`DRM_PLANE_NO_SCALING` ×2 | `mtk_plane.c` `mtk_plane_atomic_check()` |
| 4 | 格式：XR24 AR24 BX24 BA24 AB24 XB24 RG24 BG24 RG16 UYVY YUYV | `mt6572_ovl_driver_data.formats = mt8173_formats` |
| 5 | blend_modes = PREMULTI\|COVERAGE\|PIXEL_NONE；有 `alpha` 属性 | `mt6572_ovl_driver_data`；`mtk_plane.c:354` |
| 6 | **不提交 ≠ 关闭**：没提交的 plane 保留上次 SRC_CON 位，继续扫旧 buffer → 必须显式 disable | `mtk_ovl_layer_off()` 只在 `pending.enable==false` 时清位；`mtk_plane_atomic_disable()` |
| 7 | **扫描输出必须物理连续**：`mtk_gem_prime_import_sg_table()` 里 `drm_prime_get_contiguous_size(sgt) < size` → `-EINVAL` | `mtk_gem.c` |
| 8 | 有 `IN_FENCE_FD` 属性（DRM core），可选 | 板上 `z1drmtest` 实测：`plane id=35 prop IN_FENCE_FD = ...`；`drm_mode_config.c:308` |
| 9 | card1 到 **35.7 s** 才注册（不是交接文档说的 33 s）；panel/DSI 0.29 s 就 probe 了，是 component master 延迟 bind | 启动日志 0.29 s vs 35.68 s |

### 3.2 buffer 现状（这是"满血"的第二个前提）
- 板上 `/system/lib/hw/gralloc.z1.so`（18700 B，我们编的）用 **lima GEM**（`drm_gem_shmem`）分配，
  `z1a9_gpt/graphics/gralloc/lima_allocator.cpp` → `/dev/dri/renderD128` + `DRM_LIMA_GEM_CREATE`。
  shmem 页**不连续** ⇒ 按 3.1#7 **OVL 永远无法扫描这些 buffer**（设备层和 client target 都不行）。
- 连续内存来源：dts 96 MiB CMA 池 + `CONFIG_DMABUF_HEAPS_CMA=y`（乐观）/ `/dev/dri/card1` dumb
  （`mtk_gem_dumb_create` → `dma_alloc_wc`，一定连续，但 card1 要等 35 s）。
- lima 能 import 外部 dma-buf（`.gem_prime_import_sg_table = drm_gem_shmem_prime_import_sg_table`），
  所以"CMA 分配 + lima 渲染 + OVL 扫描"三方兼容是可行的。

### 3.3 Android 侧（已实测）
- `ro.hardware=z1`、`ro.hardware.egl=mesa`、`ro.hardware.hwcomposer` 未设置
  ⇒ `hw_get_module("hwcomposer")` 找 `hwcomposer.z1.so`；搜索顺序 `/odm/lib/hw`→`/vendor/lib/hw`→`/system/lib/hw`
  （从 `/system/lib/libhardware.so` 的字符串实测）。
- `/system` 以 **rw** 挂载（`fstab.z1`）⇒ `/vendor/lib/hw/*` 可由 root 热替换，**不需要刷 system 分区**。
- **板上存在可交互的串口 shell**：`console:/ $`（uid 2000 shell），
  本轮实测 `echo Z1MARK123` → 回显并执行。⇒ 后续调试不必只靠"烤肉眼看屏幕"。

## 4. 总体方案（三层递进，每层都可独立验收/回滚）

### 层 A：让 HWC2 HAL 活下来（不追求合成质量）
1. `z1_get_function()` 补齐**全部** HWC2_FUNCTION_*（2.1 语义 + 新描述符返回 nullptr 也无害，但为了保险全实现）。
   重点缺项：`CREATE_VIRTUAL_DISPLAY`(3)、`DESTROY_VIRTUAL_DISPLAY`、`SET_OUTPUT_BUFFER`、
   `SET_LAYER_DATASPACE`、`SET_LAYER_SIDEBAND_STREAM`、`GET_MAX_VIRTUAL_DISPLAY_COUNT`、
   `GET_CLIENT_TARGET_SUPPORT`、`GET_DISPLAY_NAME`、`SET_COLOR_TRANSFORM`、`SET_CURSOR_POSITION` 等。
2. `getCapabilities` 先返回 0 个能力（不声明 SKIP_VALIDATE），语义最保守。
3. `drm_open()`：等 card1（最长 60 s，500 ms 步进），成功路径全量 klog。
4. 首帧：**先试纯 plane 提交**（fbdev 已经把 CRTC modeset 好了）；失败再回退"完整 modeset"。
5. **client target 双路径**：能 import（连续 dma-buf）就零拷贝上 plane0；
   import 失败（lima/ashmem）就 **CPU 拷贝到我们自己分配的 dumb buffer** 再上屏。
   ⇒ 这一层保证"换 HAL 不会黑屏"。
6. 诊断：`hwc.z1.verbose` 属性控制 klog 详细度；每帧一行摘要；失败带 errno。

### 层 B：gralloc 换成连续内存（满血的前提）
- 新 `z1_heap.cpp`：`/dev/dma_heap/*`（优先）→ `/dev/dri/card1` dumb → lima → ashmem 四级回退，
  统一返回 dma-buf fd；保持 `private_handle_t` 64 字节 ABI 与 `z1_buffer_layout()` stride 不变。
- 部署到 `/vendor/lib/hw/gralloc.z1.so`（优先级高于 /system），**只刷 boot 或热替换即可**，不动 900 MB system 分区。
- 风险与回滚：坏 gralloc 会让整个 UI 花屏/崩溃 → 一切通过 `/data/local/tmp/z1stage/active/` 控制，
  删掉 active 里的文件 + 重启即回原厂路径。

### 层 C：真正的多图层 OVL 合成
- 组合策略（关键）：`DEVICE` 只能是 **z 序最上面的连续一段**（因为 client target 固定放最底层 plane0）。
  从最高 z 往下扫描，能放就放（≤3 层），遇到第一个放不下的，其以下全部 `CLIENT`。
- plane 分配：plane0 = client target（zpos 0），plane1..3 = device 层（按 z 升序）。
- 每层写全：FB_ID / CRTC_ID / CRTC_X,Y,W,H / SRC_X,Y,W,H(16.16) / alpha / pixel_blend_mode / rotation。
- 未用 plane 显式 `FB_ID=0,CRTC_ID=0`（3.1#6）。
- fence：第一阶段 release/retire 都返回 -1（与现在能工作的原厂 HWC1 同语义，绝不引入死锁）；
  第二阶段用 sw_sync 时间线：present N 提交后 signal N-1 的 fence，retire/release 共用一个点；
  再配 100 ms 看门狗兜底（防静态画面时 fence 永挂）。
- 验收工具：`z1kmstest`（独立 DRM 工具，不经过 SF）先证明 2/3/4 层、位置、alpha、显式 disable 都对，
  再让 SF 走同一条路。

## 6. 风险清单（每条都要有兜底）

| 风险 | 影响 | 兜底 |
|---|---|---|
| 新 HWC2 打不开 card1/提交失败 | 黑屏 | client target 拷进自建 dumb buffer；失败自动退回"什么都不做"让 SF 走 -1 fence；root 通道可删 .so 回原厂 |
| 函数表仍缺项 | 组合器照旧退出 | 全量实现 + 板上先 `z1kmstest` 证明 DRM 可用；日志直接指出缺哪个 |
| CMA heap 不存在 | gralloc 回退 lima | 走 card1 dumb；再不行保留旧 gralloc（层 A 的拷贝路径仍能出图） |
| 换 gralloc 导致 UI 崩 | 系统不可用 | active/ 机制一键回滚；fail-safe 顺序 lima→ashmem |
| 组合策略与 SF 期望不符（层序） | 画面错层 | 先只放"全屏无缩放"的顶层；用 dumpsys 对照；保守 = 全部 CLIENT（等价原厂） |
| 无 IOMMU，OVL 读不连续内存 | 花屏/黑屏 | 只 import 连续 buffer；import 失败一律 CLIENT |
| 串口传输丢字节 | 坏 .so | sha256 校验 + 失败重传；关键版本仍可刷 boot.img |
| 6 MB boot 分区 | 装不下 | ramdisk 只放 root 通道 + 首批 .so；后续全靠串口/active 目录 |
