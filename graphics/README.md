# Z1 display and graphics bring-up

The board modules in `gralloc/` and `hwcomposer/` are based on the Apache-2.0 AOSP Pie `device/generic/goldfish` fbdev gralloc and HWC1 modules. Their license headers are preserved. The stock-kernel profile keeps SwiftShader. The Linux7 profile builds Mesa 19.1.8's Lima and softpipe drivers from a checksum-pinned upstream archive and selects Mesa EGL/GLES.

Android composition still copies the completed frame to `/dev/fb0` on the CPU. The Linux7 path allocates renderable buffers as Lima GEM objects and exports them as dma-bufs; the gralloc mapper brackets CPU access with `DMA_BUF_IOCTL_SYNC`. The board configuration expects 240 x 320 RGB565, a 512-byte framebuffer line and a 480-byte source row. HWC waits for acquire fences and uses no release or retire fence because the copy is synchronous. Buffer allocation falls back to ashmem if the DRM render node is not ready, allowing software rendering to keep booting.

The factory ROM contains MT6572 Mali EGL, gralloc and HWC binaries. They cannot be loaded directly by the Android 9 image. The factory `libMali.so` imports old `GraphicBuffer`, `BufferQueue`, `BufferItem`, `Fence`, and `CallStack` symbols that are not exported by the Android 9 `libui.so`/`libgui.so`; it also depends on `libcorkscrew.so` and `libdpframework.so`, which are absent. The factory HWC additionally imports `MTKM4UDrv` and `DpBlitStream` symbols. Android 9 includes `libion.so`, but it does not export the factory gralloc's `ion_alloc_mm` or `ion_custom_ioctl` entry points. The matching MTK M4U and display-framework libraries are also absent from the candidate image.

As a reference check, the FuQuan `libMali.so` has different bytes from the factory copy but the same 171 undefined dynamic-symbol imports. Replacing only that file therefore does not close the Android 9 ABI gap. No FuQuan keylayout files or mappings are used; the physical keypad map and capacitive touchscreen navigation map stay separate in `keylayout/`.

The Mesa/Lima and dma-buf path is a build integration, not proof of runtime acceleration. Device validation still needs `/dev/dri/renderD128`, Lima GPU ID and submit logs, EGL renderer confirmation, stable SurfaceFlinger composition, `/dev/fb0` geometry, visible refresh and a producer/consumer buffer queue check. Gralloc falls back to ashmem if GEM allocation fails; Mesa EGL itself has not yet been shown to recover if the Lima DRI driver cannot initialize.
